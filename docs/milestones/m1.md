## 交付范围

在 macOS/Linux 上，同一个独立 server 与 `cove` CLI 完成本地 task/workspace 闭环：

1. **持久 server 身份与存储**：server 使用 better-sqlite3 的本地 SQLite 库保存业务记录；
   `serverId` 跨重启不变，`relayInstanceId` 每次启动新建。同一数据目录只允许一个 server。
   写操作的 operation 记录以持久键保存，重启后同一 operationId 仍去重、不重做（见“操作身份跨重启”）。
2. **Repo 注册**：在本机注册任意路径的 Git clone，校验并规范化路径；注册不导入它已有的 worktree。
3. **Task 与 workspace**：一个 task 恰好一个 workspace，一个 workspace 一个入口目录（单仓也有）。
   一次 `task create` 可配置多个挂载，创建后可继续添加或移除挂载；task 可归档/取消归档。
4. **两种挂载来源**：`checkout`（已注册 clone 或它已有的 worktree，Cove 不拥有目录）与
   `worktree`（Cove 在 workspace 目录内新建并管理的 Git worktree）。
5. **多仓准备的逐仓结果**：部分失败时保留已完成的挂载，失败挂载可重试或移除，不把部分成功显示为完成。
6. **转到独立 worktree**：把一个 checkout 挂载换成新的托管 worktree，workspace revision 加一，
   旧 run 保留原绑定（范围见决策 D3）。
7. **Tab 与 run**：tab 是 task 下持久的逻辑终端记录，run 是它的一次 PTY 运行实例；
   默认 cwd 为 workspace 入口目录；停止、手动重开（新 runId）、查看历史 run。终端链路沿用 M0。
8. **重启语义**：server 正常停止或崩溃后重启，task/workspace/挂载/tab/run 记录保留；
   旧实例的 run 显示为会话中断且不可核实，不显示为存活，不自动重开或重跑任何命令。
9. **CLI 完整操作**：以上每项能力都有 `cove` 子命令与 JSON 输出，经同一 HTTP RPC 领域方法执行；
   包括本机初始化与 `workspaceRoot` 设置。

M0 已合入的终端链路（protocol、terminal-engine、terminal-worker、client、terminal-web、
harness）保持现状。M1 只在 run 的创建与记录处接入，不重构终端恢复、focus 或流控。
M0 测试 harness 继续作为交互载体：tab 的 run 也是普通终端 run，可在 harness 中 attach。

### 明确不做

- 跨主机迁移、rollout 复制、跨主机 repo 映射表（M4）；远程接入、配对、设备授权、tsnet、服务安装与开机自启（M2）。
- Electron、RN/WebView、Web App 及任何新的 GUI（M3 与二期）；业务事件 WebSocket 订阅（M3 有 GUI 时再加，
  M1 的资源都带 revision，CLI 按需读取）。
- 独立 PTY keeper、终端画面/恢复基线/scrollback 落盘、重启后接管旧 PTY。
- 普通目录（`directory`）挂载；转 worktree 时携带未提交改动（见 D3）。
- 普通终端活动分类（执行中/近期/闲置）与 shell integration、agent 识别与 agent 工作状态、agent hook。
- 定时任务、chat、Shepherd、managed agent。
- 计划重启前导出单独的 tab 清单文件：tab/run 日常持久化在库中，`cove tab list` 即是清单（见 D9）。
- 不新增 npm package；领域代码是 `apps/server` 的内部模块（[工程 §1](../engineering-plan.md#1-已确认单仓库建议按部署入口和真实依赖边界组织)）。

## 验收场景

每个场景是一个启动编译产物（`cove-server`、`cove` CLI）的自动化测试，在 macOS 与 Ubuntu CI 上运行，
结果只有通过或失败。测试在临时目录中用 `git init` 建临时仓库，使用独立的临时 Cove 数据目录与
workspace 根目录，不触碰真实 `~/.cove` 或用户仓库。CI 绿灯就是证据，不另行封存。
写命令都接受 `--operation-id`，测试借此在重启前后重发同一操作。
S2、S5 中经入口访问 checkout 的断言取决于 D2（由 P0 确定），S6 取决于 D3、D10；下表按推荐选项书写。

另需用户做约一小时的真实使用试用，检验自动化覆盖不到的真实 Git/agent 行为：

- 注册两个真实仓库；创建调查 task 挂载已有 checkout，在 workspace 入口启动 Claude Code、Codex 或 TraeX，
  让 agent 搜索、读取、修改挂载中的文件并执行 git 命令，确认 D2 选定的方式下 agent 能实际工作。
- 创建两仓 task（各建新 worktree），在 agent 中分别修改、提交；确认分支和提交只出现在对应 worktree。
- 将调查 task 转到独立 worktree，确认旧 tab 仍指向原位置，新 tab 在新 worktree。
- 有 agent 运行时重启 server：确认显示为会话中断而非存活；手动重开 tab 后用 agent 自身的 resume 继续
  （是否能续上是 agent 的行为，只作观察，不是 Cove 的验收）。
- 通过 harness attach tab 的 run，确认 M0 终端链路在 task 场景中照常工作。

## 操作身份跨重启

用户此前倾向于让控制与领域请求都带请求键并保持幂等。M1 据此落实
[relay-protocol §11.3](../relay-protocol.md#113-去重并发与保存期限)，并修改 M0 的实现：

- **持久身份与执行隔离分开。** 操作记录的键改为 `(serverId, principalId, operationId)`，不再含
  `relayInstanceId`；本机 principal 为持久的本机所有者，不随启动变化。`relayInstanceId` 只作为
  针对具体 run 的执行隔离条件（如停止某个 run 必须属于当前实例）。
- **先查记录，再做隔离检查。** 收到写请求时先按持久键查找：已有记录且指纹相同则返回原记录，
  即使其中的 run 属于旧实例；指纹不同返回 `OPERATION_ID_CONFLICT`；没有记录时才检查 expected
  实例等前提，旧实例的新请求照常拒绝。M0 terminal 操作目前先拒旧实例再查记录，需要调换。
- **未决操作不重做。** 启动时把旧实例遗留的 accepted/running 操作转入核实流程；不能证明结果的
  标为 requires_attention。同一 operationId 重发只返回该记录；继续或放弃是带新 operationId 的显式命令。
- **客户端接受旧实例的历史结果。** `operation.get` 与重发返回的记录可以引用旧实例的 run；
  客户端按方法表的读写分类处理所有方法，不再只认 M0 的两个写方法。
- 协议首个正式版本前不维护兼容，这一变更不提升协议版本（[relay-protocol §10](../relay-protocol.md#10-发布门槛与验证)）。

## 任务拆分

每个任务一个 PR，由独立 subagent 在各自 worktree 实现；每个 PR 带上自己负责的场景测试。
文件归属为排他写入范围。共享入口各有唯一写入者：

- **RPC 方法表、server 分派与客户端**：T0 唯一写入。T0 定义全部 M1 方法，把 server 分派改为按方法表查
  `apps/server/src/rpc/<领域>.ts` 处理模块，并为每个领域建一个只返回 `CAPABILITY_UNAVAILABLE` 的初始模块；
  之后各任务只替换自己领域的模块，不再改 `http-rpc.ts`、方法表或分派表。客户端改为按方法表的读写分类与
  实例绑定规则处理所有方法，新方法无需再改 `packages/client`。
- **数据库 schema**：T1 按 T0 契约一次建好 M1 全部表（迁移 001）与存储层的打开、事务、迁移执行接口；
  各领域的查询代码由各任务写在自己的领域模块里。确需改表时，任务新增一个由协调者在派发时分配编号的
  迁移文件，不修改已有迁移。
- **CI 测试清单**：`scripts/ci-test-gate.mjs` 要求每个测试文件都登记在 `requiredSuites`，缺登记或缺文件都会失败。
  T1 为 `apps/cli/tests/m1/` 增加按文件登记的方式：每个测试文件旁放同名 `.suite.json`（声明最少测试数），
  门禁检查测试文件与登记文件一一对应且数量达标。各任务只新增自己的测试与登记文件。该门禁改动随 T1 一起 review。

### D2. 已有 checkout 的引用方式与新 worktree 的放置

托管 worktree 直接建在 `<入口>/<挂载名>`，这一点各选项相同。checkout 挂载要分开处理四个风险：

1. **搜索遍历**：ripgrep 等搜索工具默认不跟随符号链接，agent 从入口搜索可能看不到 checkout 的内容。
2. **规范路径授权**：agent 把链接解析为真实路径后，可能视为 cwd 之外，从而要求授权或被沙箱拒绝写入
   （例如只放行 cwd 与显式附加目录的写入沙箱）。
3. **文件监听**：监听器可能不跟随链接，或以真实路径上报事件。
4. **绑定稳定性**：替换绑定会改变仍在运行的会话经入口看到的内容。

| 选项 | 内容                                                                                                                                                                                                                                                               | 覆盖的风险                                                                             | 影响                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| A    | 入口 `<入口>/<挂载名>` 为指向真实路径的符号链接；入口目录内生成一份挂载清单（各挂载名、真实路径、来源类型）；tab 启动已知 agent（Claude Code、Codex）时，启动配方把 checkout 的真实路径作为附加目录传入（如 `--add-dir`）；替换绑定前要求该 workspace 没有存活 run | 1 由清单与真实路径缓解；2 由附加目录解决；3 agent 以真实路径工作；4 由“先结束 run”保证 | 从入口仍能直接看到 checkout；依赖各 agent 的附加目录参数，未知 agent 只得到清单     |
| B    | 版本化入口 `<入口>/r<revision>/<挂载名>`，每个 run 的 cwd 为启动时的 revision 目录                                                                                                                                                                                 | 只解决 4；1–3 不变，仍需与 A 或 C 的访问方式组合                                       | cwd 随 revision 变化，agent 按 cwd 保存的会话历史会分裂，目录层级更深               |
| C    | 入口目录只放托管 worktree 与挂载清单，不为 checkout 建链接；agent 经清单中的真实路径与启动配方的附加目录访问 checkout                                                                                                                                              | 2、3 不存在；1 由清单缓解；4 无链接可变                                                | 从入口看不到 checkout，agent 必须读清单；只挂 checkout 的调查 task 的入口里只有清单 |

checkout 挂载只能引用已注册 clone 本身，或与它共享同一 Git common dir 的已有 worktree（显式给出路径）；
被选中的已有 worktree 不因此成为 Cove 可删除的资源。

可行性在实施早期验证，不等到试用：P0 探针在本机临时仓库上，用 Claude Code 与 Codex 分别对 A 与 C
做搜索、读取、修改与 git 操作，记录各风险的实际表现；A 不可用时选 C。CI 场景 S2、S5 覆盖 Git 与
普通 shell 经入口的读写，不覆盖 agent 行为。

Orca 的多仓 task 把已有链接 worktree 用 `git worktree move` 移进根目录（移动前做存活检查），
主 checkout 则留在根目录外，agent 从根目录看不到；Cove 已确认不移动用户目录。

**推荐 A，以 C 为备选，由 P0 在 T3a 合入前确定**（推荐有变化：原推荐 A、试用后再评估 B；B 不解决链接带来的
搜索、授权与监听问题，改为以 C 为备选）。

### D8. “tab/run”的具体含义

| 选项 | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                | 影响                                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| A    | Tab：属于 task 的持久记录（名称、启动配方 = 可执行文件与参数或默认登录 shell、cwd = 入口目录或某挂载）。Run：tab 的一次 PTY 实例（runId、启动时的 workspace revision 与挂载映射、开始/结束时间、退出码或结束原因）。`tab create` 默认立即启动首个 run；`tab reopen` 用记录的配方新建 run；`tab stop` 停当前 run；`tab close` 仅在无存活 run 时删除记录。M0 的 `terminal create` 保留，产生不属于 tab 的 run，同样记录并适用重启语义 | 与 [终端设计 §12.1](../terminal-architecture.md#121-逻辑-tab-与运行实例分开) 一致；不保存环境变量，只注入 `COVE_TASK_ID` 等少量标识 |
| B    | 不引入 tab，run 直接属于 task                                                                                                                                                                                                                                                                                                                                                                                                       | 少一层；无法表达“同一个逻辑终端重开”，与已确认的 tab 记录与手动重开冲突                                                             |
| C    | A，但 tab 不保存启动配方，重开总是启动 shell                                                                                                                                                                                                                                                                                                                                                                                        | 更简单；重开 agent 需要用户每次重输命令                                                                                             |

### D10. 托管 worktree 的删除

| 选项 | 内容                                                                                                                                                                                                                                                                                                                       | 影响                                                                  |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| A    | M1 不删除目录：移除挂载只解除关系，托管 worktree 留在磁盘，由用户手动 `git worktree remove`                                                                                                                                                                                                                                | 最安全；托管目录会累积，且手动删除后记录变为“缺失”                    |
| B    | 移除挂载时可选删除托管 worktree，按引用检查：工作区干净（含未跟踪文件）；没有任何其他 workspace（含已归档）以 checkout 方式挂载它；所有引用它的 workspace 中，没有 cwd 或挂载映射落在它下面的存活 run；全部满足才用 `git worktree remove`（不加 `--force`），**保留分支**；拒绝时列出脏文件、引用它的 workspace 与相关 run | 保留分支即保留全部提交；引用与存活 run 检查覆盖设计 §6 的共享引用要求 |
| C    | B 再加删除分支（要求分支已合入或已推送）                                                                                                                                                                                                                                                                                   | 更彻底；“已推送/已合入”的判断依赖远端状态，误删风险更高               |

D2 允许以 checkout 方式挂载同一 clone 的已有 worktree，因此 task B 可能引用 task A 的托管 worktree；
B 选项因此不做“解除引用后再删”的级联，只拒绝并说明，由用户先移除其他挂载。
存活 run 的判断用 T4 记录的 run 挂载映射，所以删除放在 T5。

Orca 删除时默认要求干净，分支仅在已合入或已发布时删除。

**推荐 B（已加入跨 workspace 的引用与存活 run 检查）**。checkout 挂载与外部 worktree 在任何选项下都不删除。
