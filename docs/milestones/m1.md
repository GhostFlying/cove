## 交付范围

在 macOS/Linux 上，同一个独立 server 与 `cove` CLI 完成本地 task/workspace 闭环：

1. **持久 server 身份与存储**：server 使用 better-sqlite3 的本地 SQLite 库保存业务记录；
   `serverId` 跨重启不变，`relayInstanceId` 每次启动新建。同一数据目录只允许一个 server。
   写操作的 operation 记录以持久键保存，重启后同一 operationId 仍去重、不重做（见“操作身份跨重启”）。
2. **Repo 注册**：在本机注册任意路径的 Git clone，校验并规范化路径；注册不导入它已有的 worktree。
3. **Task 与 workspace**：一个 task 恰好一个 workspace，一个 workspace 一个入口目录（单仓也有）。
   一次 `task create` 可配置多个挂载，创建后可继续添加或移除挂载；task 可归档/取消归档。
4. **两种挂载来源**：`checkout`（已注册 clone 或它已有的 worktree，Cove 不拥有目录；按约定只用于
   只读任务）与 `worktree`（Cove 在 workspace 目录内新建并管理的 Git worktree，创建前 fetch 远端，
   默认基于远端主分支）。
5. **多仓准备的逐仓结果**：部分失败时保留已完成的挂载，失败挂载可重试或移除，不把部分成功显示为完成。
6. **转到独立 worktree**：把一个 checkout 挂载换成新的托管 worktree，workspace revision 加一，
   旧 run 保留原绑定（范围见决策 D3）。
7. **Tab 与 run**：tab 是 task 下持久的逻辑终端记录，run 是它的一次 PTY 运行实例；
   默认 cwd 为 workspace 入口目录；停止、手动重开（新 runId）、查看历史 run。终端链路沿用 M0。
8. **重启语义**：server 正常停止或崩溃后重启，task/workspace/挂载/tab/run 记录保留；
   旧实例的 run 显示为会话中断且不可核实，不显示为存活，不自动重开或重跑任何命令。
9. **CLI 完整操作**：以上每项能力都有 `cove` 子命令与 JSON 输出，经同一 HTTP RPC 领域方法执行；
   包括本机初始化与 `workspaceRoot` 设置。

M0 已合入的终端链路（protocol、terminal-engine、terminal-worker、client、terminal-web、
harness）保持现状。M1 只在 run 的创建与记录处接入，不重构终端恢复、focus 或流控。
M0 测试 harness 继续作为交互载体：tab 的 run 也是普通终端 run，可在 harness 中 attach。

### 明确不做

- 跨主机迁移、rollout 复制、跨主机 repo 映射表（M4）；远程接入、配对、设备授权、tsnet、服务安装与开机自启（M2）。
- Electron、RN/WebView、Web App 及任何新的 GUI（M3 与二期）；业务事件 WebSocket 订阅（M3 有 GUI 时再加，
  M1 的资源都带 revision，CLI 按需读取）。
- 独立 PTY keeper、终端画面/恢复基线/scrollback 落盘、重启后接管旧 PTY。
- 普通目录（`directory`）挂载；转 worktree 时携带未提交改动（见 D3）。
- 普通终端活动分类（执行中/近期/闲置）与 shell integration、agent 识别与 agent 工作状态、agent hook。
- 定时任务、chat、Shepherd、managed agent。
- 计划重启前导出单独的 tab 清单文件：tab/run 日常持久化在库中，`cove tab list` 即是清单（见 D9）。
- 不新增 npm package；领域代码是 `apps/server` 的内部模块（[工程 §1](../engineering-plan.md#1-已确认单仓库建议按部署入口和真实依赖边界组织)）。

## 验收场景

每个场景是一个启动编译产物（`cove-server`、`cove` CLI）的自动化测试，在 macOS 与 Ubuntu CI 上运行，
结果只有通过或失败。测试在临时目录中用 `git init` 建临时仓库，需要远端时另建一个本地 bare 仓库作为

CI 绿灯就是证据，不另行封存。写命令都接受 `--operation-id`，测试借此在重启前后重发同一操作。

## 操作身份跨重启

用户此前倾向于让控制与领域请求都带请求键并保持幂等。M1 据此落实
[relay-protocol §11.3](../relay-protocol.md#113-去重并发与保存期限)，并修改 M0 的实现：

- **持久身份与执行隔离分开。** 操作记录的键改为 `(serverId, principalId, operationId)`，不再含
  `relayInstanceId`；本机 principal 为持久的本机所有者，不随启动变化。`relayInstanceId` 只作为
  针对具体 run 的执行隔离条件（如停止某个 run 必须属于当前实例）。
- **先查记录，再做隔离检查。** 收到写请求时先按持久键查找：已有记录且指纹相同则返回原记录，
  即使其中的 run 属于旧实例；指纹不同返回 `OPERATION_ID_CONFLICT`；没有记录时才检查 expected
  实例等前提，旧实例的新请求照常拒绝。M0 terminal 操作目前先拒旧实例再查记录，需要调换。
- **未决操作不重做。** 启动时把旧实例遗留的 accepted/running 操作转入核实流程；不能证明结果的
  标为 requires_attention。同一 operationId 重发只返回该记录；继续或放弃是带新 operationId 的显式命令。
- **传输绑定与执行前提分开。** 传输绑定是每次请求时客户端与当前 server 的关系（serverId、
  当前 relayInstanceId、协议版本），由 header 与响应逐次核对，serverId 不符一律拒绝。执行前提是操作
  创建时写进参数的条件，如 `terminal.create`/`terminal.stop` 的 `expectedRelayInstanceId` 与 run 引用；
  它们属于原操作，留在参数与指纹里（`canonicalOperationIntent` 不变），只在服务端没有该操作记录时才检查。
  客户端准备写请求时只核对 serverId，不再要求执行前提等于当前实例（改 `prepareCall` 的
  `paramsMatchInstance`），让旧实例参数到达服务端去重；`operation.get` 去掉 `expectedRelayInstanceId`，
  按 serverId 与 operationId 查询。
- **重发用原请求，且只发往原 server。** CLI 在首次发送写请求前，把原 serverId、方法与不可变的完整参数
  保存到数据目录下的本机待定记录（[relay-protocol §11.2](../relay-protocol.md#112-只保留两个执行标识)：
  客户端提交前生成并保存 operationId）；`cove operation resend <operationId>` 先确认当前连接的 serverId
  与记录相同（relayInstanceId 可以不同），不同则拒绝且不发送，相同才原样重发保存的方法与参数。领域方法（repo/task/mount/tab/config）没有实例前提，
  用 `--operation-id` 重建的参数指纹相同；终端方法若按当前实例重建参数，指纹不同，返回
  `OPERATION_ID_CONFLICT`，这是有意的：那是新的意图。待定记录只写一次；复用 operationId 时 CLI 先读已保存的
  记录，serverId、方法与规范意图都相同才发送保存的请求，否则在本机拒绝、不发送，提示换新的 operationId
  （否则服务端可能执行一个 `resend` 无法复现的请求）。记录在发送前连同所在目录一起 fsync。
- **客户端接受旧实例的历史结果。** `operation.get` 与重发返回的记录可以引用旧实例的 run；
  客户端按方法表的读写分类处理所有方法，不再只认 M0 的两个写方法。
- **分两步交付，各自可构建。** T0 改契约、客户端，并做最小的 server 适配：`operation-receipts.ts` 与
  `terminal-operations.ts` 改用新键，调换为先查记录再检查前提，记录仍在内存，附进程内单元测试；
  T0 自身 CI 全绿。T1 再把记录持久化、加启动核实，并以 S10 验收跨重启行为。
- 协议首个正式版本前不维护兼容，这一变更不提升协议版本（[relay-protocol §10](../relay-protocol.md#10-发布门槛与验证)）。

## 任务拆分

每个任务一个 PR，由独立 subagent 在各自 worktree 实现；每个 PR 带上自己负责的场景测试。
文件归属为排他写入范围。共享入口各有唯一写入者：

- **RPC 方法表、server 分派与客户端**：T0 唯一写入。T0 定义全部 M1 方法，把 server 分派改为按方法表查
  `apps/server/src/rpc/<领域>.ts` 处理模块，并为每个领域建一个只返回 `CAPABILITY_UNAVAILABLE` 的初始模块；
  之后各任务只替换自己领域的模块，不再改 `http-rpc.ts`、方法表或分派表。客户端改为按方法表的读写分类与
  实例绑定规则处理所有方法，新方法无需再改 `packages/client`。
- **数据库 schema**：T1 按 T0 契约一次建好 M1 全部表（迁移 001）与存储层的打开、事务、迁移执行接口；
  各领域的查询代码由各任务写在自己的领域模块里。确需改表时，任务新增一个由协调者在派发时分配编号的
  迁移文件，不修改已有迁移。
- **CI 测试清单**：`scripts/ci-test-gate.mjs` 要求每个测试文件都登记在 `requiredSuites`，缺登记或缺文件都会失败。
  T1 为 `apps/cli/tests/m1/` 增加按文件登记的方式：每个测试文件旁放同名 `.suite.json`（声明最少测试数），
  门禁检查测试文件与登记文件一一对应且数量达标。各任务只新增自己的测试与登记文件。该门禁改动随 T1 一起 review。

## 已决策

用户于 2026-10-15 对 D1–D10 作出以下决定。已确认的既有决策（SQLite + better-sqlite3、一个 task 一个
workspace、统一可配置 workspace 根目录、agent 默认 cwd 为 workspace 入口、列表只展示 Cove 记录、无 keeper、
终端持久化方案 A、CLI 为完整操作入口）不变。Orca 对照见文末。

### D1. Workspace 布局、fetch 与基准（选 A，基准规则按用户要求修改）

- 布局：`<workspaceRoot>/<slug>-<短 ID>/<挂载名>`。slug 由 task 标题生成、创建时固定，改标题不改目录；
  挂载名默认取 repo 显示名，冲突时要求指定。目录名只是记录，不从目录名反推身份。默认 `workspaceRoot` 为 `~/.cove/workspace`。
- 分支名默认 `cove/<slug>`，可用 `--branch` 覆盖。
- **创建 worktree 前自动 fetch 来源 clone 的远端**；fetch 失败（离线、认证等）则整个挂载失败、不创建任何东西，
  错误提示可用 `--no-fetch` 改用本地已有的远端跟踪分支。
- **默认基准是远端主分支**（如 `origin/main`），可用 `--base <ref>` 覆盖。主分支按以下顺序解析：
  repo 注册中的 Cove 主分支设置；`origin/HEAD`；`git ls-remote --symref origin HEAD`；远端上存在的
  main、master、trunk、develop 中的第一个。都没有则失败并要求传 `--base`，**绝不静默回退到本地 HEAD**。
- 转到独立 worktree（D3）使用同一基准规则。
- 未选：B（只用不透明 ID，人难以分辨任务）；C（按仓库分组，与“每个 workspace 一个入口”冲突）。

### D2. checkout 挂载的访问方式（选 C，由 P0 结果于 2026-10-15 决定，见 #92）

托管 worktree 直接建在 `<入口>/<挂载名>`。checkout 挂载有四个风险：搜索工具默认不跟随符号链接；
agent 按真实路径判断授权；文件监听可能不跟随链接；替换绑定会改变运行中会话经入口看到的内容。

- **C（已选）**：入口目录只放托管 worktree 与挂载清单 `cove-workspace.json`（每个挂载的名称、真实路径、
  来源类型、只读标记与状态），不为 checkout 建符号链接或目录；agent 经清单中的真实路径访问 checkout。
  清单文件名不以点开头，因为搜索工具默认跳过隐藏文件；挂载名不能取该文件名。
- 选择理由（P0，#92）：A 的符号链接不能让 checkout 被默认的递归搜索看到（ripgrep、Claude 的 Grep 与
  `grep -r` 都不跟随链接）；Claude Code 与 Codex 在 A 与 C 中都先读清单、再全程使用真实路径，没有一次经
  链接路径工作；Git 与工具输出也报告真实路径，A 只会造成路径混杂。C 在每次运行中结果相同，且没有
  “替换绑定改变链接目标”的问题。文件监听未探测。
- agent 启动规则（M1 不实现 agent 启动，只记录）：Claude Code 以 `--add-dir <checkout 真实路径>` 传入
  checkout；Codex **不**传 `--add-dir`，因为其含义是可写，而 checkout 按约定只读（D4），`read-only` 沙箱已能读取
  任意路径；启动提示中指明挂载清单。
- 未选 A：入口 `<入口>/<挂载名>` 为指向真实路径的符号链接，加挂载清单与附加目录；理由见上。
- 入口与数据库的顺序（T3a）：先在数据库中记录 workspace 及每次挂载变化，再写入口目录与清单。
  新入口以非递归 mkdir 直接占用最终路径（0700；已存在任何东西，包括空目录，即报告占用且不触碰），在其中以
  O_EXCL 建临时清单（0600，已落盘），再以 link(2) 发布为 `cove-workspace.json`（从不替换已有文件）；已有入口
  的清单（每次读取清单都在读取前后经文件句柄核对设备号、inode、变更时间与大小不变，读取期间的原地改写
  因而被拒绝；检查时读取清单后也核对其文件名仍指向所读的文件）先核对仍是检查时的同一文件（设备号、inode、变更时间、大小与逐字节相同的内容），改名前再以 lstat 核对该文件名仍指向
  这一文件（设备号、inode、变更时间与大小）才替换；link 或改名前还核对临时清单仍是本次创建的文件且与所写字节逐字节一致
  （读取前后经文件句柄核对，之后其文件名仍须指向通过核对、变更时间与大小都相同的这一文件），
  否则拒绝并保留替换者。内容一律按字节比较而非解码后的文本：每个非法 UTF-8 序列都解码为 U+FFFD，不同字节
  可能解码为相同文本。入口、根目录及其上各级目录落盘后才记为该 revision 已写入。
  每个 workspace revision 带有一次“发布缺失入口”的资格，与推进 revision 的变化在同一事务中提交
  （`entry_attempted_revision`，迁移 002）。首个尝试者在发布前以一条语句持久、原子地取得它：通常是提交该变化
  的请求；该请求在提交后崩溃或丢失应答时，由之后的读取（包括重启后）取得。只有核实本次发布未在入口路径
  留下任何东西（占用前即发现路径已被占用，或普通失败且占用的目录已移除）时才归还资格；已占用入口目录、
  其中却出现他人清单时，目录留下，资格不归还。取得资格后崩溃或结果不确定的发布不会重做，入口报告 missing，
  直到下一个 revision。
  当前 revision 已记为写入或其资格已被取得时，入口缺失说明它已发布（或可能已发布）后被外部删除：读取报告
  missing，下一次挂载变化带来新的资格时重建。按回执重发或发现相同请求已先提交的请求自身不写；任何人都可把
  Cove 自己入口中的旧清单更新到当前 revision。读取返回的 `entryState`
  属于其返回的 workspace revision：读取期间有变化提交时，重新读取记录（有限次数），仍不一致则报告 pending。
  状态：ready（Cove 的目录，清单与该 revision 和挂载列表的字节完全一致）、pending、missing、unavailable。
- 入口归属（T3a）：入口路径上只有本用户的目录、且其清单属于同一 workspace（kind、version、task 与
  workspace ID）时才是 Cove 的入口。其他占用者（Cove 未发布的目录、文件、符号链接、其他 workspace 的清单、
  不是合法 UTF-8、无法解析或超过上限的清单）报告为 unavailable；`task create` 时入口路径已被占用则以
  `WORKSPACE_ENTRY_UNAVAILABLE` 拒绝且不记录。清单上限由协议上限推导（16 个挂载、每个路径按 JSON 最坏
  转义计），不是估计值。
- 威胁模型与保证（T3a）：Cove 不防御同一用户下的恶意进程；Node 没有 openat(2)/renameat2(2)，写入无法固定
  到已检查的目录。Cove 保证：在它能察觉的任何事件顺序下，从不接管或覆盖不属于自己的路径或清单。做法是每次
  创建（占用入口目录、建临时清单）前立即核对根目录仍解析为自身且是同一目录（设备号与 inode），入口内的创建
  还核对入口仍是自己创建或检查过的目录；创建一律排他（非递归 mkdir、O_EXCL|O_NOFOLLOW）；新清单以 link(2)
  发布，从不替换；替换清单前核对其仍是检查时的同一文件与内容，并在改名前立即核对文件名仍指向它；link 或
  改名前立即核对临时清单仍是自己写的文件与内容。剩余窗口：每次最后核对与其保护的系统调用之间的瞬间（此时
  替换路径分量、清单或临时清单不会被察觉，调用会跟随它）。调用后的核对（根目录仍解析为同一目录、入口仍是
  同一目录）只能发现核对时仍在的目录替换：只替换清单或临时清单、或在这些核对前又换回的替换，可能以
  `written` 完成。变更时间的精度是文件系统时钟的精度：在其同一刻内保持长度不变的原地改写，或在同一 inode 号上
  以相同长度重建的文件，无论内容如何都不会被这些核对察觉；按威胁模型保留此窗口，不再读一次。发布还有一个窗口：mkdir 占用入口与 lstat 记录所建目录（directoryId）之间换入的目录会被当作
  占用（核对了它是同一根目录下的目录，但不能证明是 mkdir 所建）。在占用入口目录与发布清单之间崩溃，会留下
  没有清单的空目录（或只含 `.cove-workspace.json.*.tmp`），
  与他人的目录无法区分，因此报告 unavailable，直到操作者移除。Cove 只删除本次调用自己创建且已核实的东西
  （自己的临时文件、仍为空的自己占用的目录），不删除其他任何内容，也从不写入 checkout 目录。
- checkout 身份（T3a）：checkout 仍是被准入的绑定，当且仅当其记录路径仍是同一真实目录（途中无符号链接）、
  Git 报告的顶层是该路径、common dir 与当前 repo 注册一致，且该路径未被记为托管 worktree。每次读取都核对：
  不符报告 missing，无法核对报告 unavailable。Git 拒绝该目录而 `.git` 仍在（元数据无权读取、safe.directory
  所有权拒绝、损坏）属于无法核对；只有 `.git` 不在，或 linked worktree 的 `.git` 文件所指目录不在，才证明
  绑定已不在（missing）。T2 注册时的拒绝不变。读取预算：一次读取在约 3 秒内返回（客户端请求超时为 5 秒），
  到期未完成的核对与入口检查报告 unavailable；`task list` 的一页中相同的 checkout 只核对一次。服务的所有
  Git 发现共享有限的并发槽位（默认 4），占用槽位的时间不超过其截止时间（读取的截止时间；写入每次发现
  20 秒）：截止后不再启动 Git 命令，每条命令只得到剩余时间，文件系统探测到期即不再等待。等待槽位的请求
  到截止时间即离开队列、不启动任何东西；空出的槽位按请求轮流分配，大的 `task list` 不会让单个 `task get`
  排在其全部核对之后；轮到时已过截止时间的等待者也不获得槽位。截止时间只限制应答，不限制已开始的文件系统
  操作：服务对已启动且尚未结束的文件系统工作设上限（默认 16，许可持有到操作本身结束）。请求的所有文件系统
  操作都经过它：checkout 核对、发现中的探测、入口物化，以及写入在事务前的检查（checkout 真实路径、workspace
  根目录与入口路径）。一个请求至多同时持有一半许可，其余工作（如大的一页中的其他条目）排队等待到截止时间，
  空出的许可按请求轮流分配，因此超过上限的健康页面也能完整核对；只有全部许可都被已过截止时间、尚未结束的
  工作占用时才不等待、不启动任何东西（已在等待的请求在最后一个占用者的截止时间过去时同样立即得到应答；放弃应答
  只在 performance.now() 确已到达截止时间后发生，计时器提前触发时重新计时）：读取报告 unavailable，写入以 `BUSY` 拒绝（未接受、不记录，稍后可用
  同一请求重试），而不是报告关于路径的结论（如 `NOT_A_GIT_REPOSITORY`）。写入的每一步（每次文件系统检查与 Git 发现）在 20 秒内应答；
  已开始却没有应答的一步（包括 checkout 真实路径的解析）使写入以 `GIT_UNAVAILABLE` 拒绝（workspace 根目录与
  入口路径为 `WORKSPACE_ENTRY_UNAVAILABLE`），写入从不缺少所需的检查而继续。许可或槽位交给等待者后，
  开始工作前再核对一次其截止时间，已过则立即归还、不启动。
  并发请求共享同一 checkout 进行中的核对，每个 workspace 至多一个进行中、一个等待中的入口物化；每个请求只
  观察共享工作到自己的截止时间，放弃时即被移除，超时的读取不会在永不结束的工作上积累。截止时间已过则不启动
  任何工作，被放弃的操作失败时也有处理，不会成为未处理的拒绝。写入提交后最多等待其入口物化 20 秒（可配置），
  之后以已记录的操作应答，未完成的部分由之后的读取修复。
  写入在事务前对每个新 checkout 再核对一次，只剩该 Git 查询与提交之间无法覆盖（Git
  不能在存储事务内运行），由下一次读取报告。按 T2 的身份规则，在同一路径重建的 clone 与原注册是同一 clone。
- 响应大小（T3a）：每条被接受的 task 记录都能放进一次 `task get` 响应（按最长标题、最大计数、最长状态、
  每个 checkout 与 128 个 task 共享的最坏情况计算，留出信封余量）；写入在提交前拒绝（`INVALID_ARGUMENT`）
  会使其超出的 `task create` 或 `mount add`。`task list` 在会超出响应字节数或 4096 个 JSON 值上限的 task 之前
  结束一页，`nextAfterTaskId` 为本页最后一个 task，因此一页可能少于所请求的数量。
- checkout 挂载只能引用已注册 clone 本身，或与它共享同一 Git common dir、且**不由 Cove 管理**的已有
  worktree（显式给出路径）；被选中的已有 worktree 不因此成为 Cove 可删除的资源。以 checkout 方式挂载
  Cove 为任何 workspace 创建的托管 worktree（包括已归档 task 的）一律拒绝，错误 kind 为
  `MANAGED_WORKTREE_NOT_MOUNTABLE`。
- 仍有挂载（含已归档 task 的挂载）引用某 repo 时，`repo remove` 被拒绝（`REPO_IN_USE`）：已归档 task
  保留挂载，取消归档时不能出现 repo 已不存在的挂载；先移除这些挂载（已归档 task 也允许移除挂载）。
- 未选：B（版本化入口），它只解决绑定稳定性，且使 cwd 随 revision 变化、agent 会话历史分裂。

### D3. 转到独立 worktree（选 B）

只从提交开始，不携带改动：展示来源的已暂存、未暂存、未跟踪改动，原样留在来源，不 stash、reset 或切换来源分支。
用户的理由：要改代码的任务一开始就不应使用已有 checkout，转换后从干净的基准开始即可。
未选：A（不做转换，推迟设计 §3 的工作流）；C（携带改动，复杂度接近迁移）。

### D4. 共享 checkout（选 A，不加锁）

只展示共享关系，不加锁。用户约定：共享或已有 checkout 挂载只用于只读任务（阅读，至多构建或运行测试），
不支持在其中改代码。这是文档约定，Cove 不强制；CLI 在 checkout 挂载的帮助与输出中注明。
共享关系包括已归档 task 的挂载：归档只改可见性，已归档 task 保留挂载并可能仍有 run 在使用该 checkout；
该挂载移除后关系才结束（T3a）。
未选：B（只读意图无法强制，易被误解为已隔离）；C（强制确认参数，增加交互而无实际保护）。

### D5. 数据库位置、schema 与迁移（选 A）

数据目录 `~/.cove`（可用 `COVE_HOME` / `--home` 覆盖，测试用临时目录），库在 `~/.cove/server/cove.db`，
目录权限 0700；手写顺序 SQL 迁移，以 `PRAGMA user_version` 记版本，启动时在一个事务里前进迁移，迁移前用
`VACUUM INTO` 留备份；库版本高于构建时拒绝启动且不改文件；WAL + `synchronous=FULL`。持久 serverId 存在库内；
数据库 schema 版本与协议版本、配置 schemaVersion 互相独立。
未选：B（查询构建器及其迁移工具，增加依赖与生成步骤）；C（不写迁移，试用记录会随升级丢失）。

### D6. 数据库执行位置（选 B，由探针结果于 2026-10-16 决定）

存储层在 runtime 进程内的一个专用 `worker_threads` 数据库 worker 中运行 better-sqlite3，主线程经异步 API 调用；
每个业务操作仍是 worker 内的一个完整短事务，存储模块只暴露完整业务操作的函数，不跨调用拆开事务；
`busy_timeout` 为 0（单实例独占库，不应有锁等待）。领域调用方改为等待异步结果。实现由 F-D6B 完成。
原因：PTY 与解析虽在 worker 子进程，runtime 主线程仍负责终端输入输出转发、WebSocket 投递与恢复计时器，
主线程上的同步提交会推迟这些路径；探针在 Linux 上测到了这种推迟（见下文结果）。

最初选 A（主线程同步调用），条件是 T1 的探针确认无阻塞。探针给出 B，但当时 T1 已经合入，
改用 B 涉及存储层与全部领域调用方，不能再放进 T1，因此另立 F-D6B 任务。

#### 探针方法

探针（`apps/cli/tests/m1/d6-latency-probe.mjs`）启动编译产物，按[工程 §9.3](../engineering-plan.md#93-测试分层)
单独执行，不进入普通 `pnpm test` 与 CI 门禁：

- **有界负载**：8 个终端由固定脚本输出，全部由一个客户端订阅；规定速率为每路 64 KiB/s，
  `--output-kib-per-second` 可降低每路速率，报告同时记录实际与规定速率。另一个客户端每 50 ms 发送一个按键
  并测量回显延迟；写入负载为每秒 20 个完整业务写操作（`config.set`）。
- **对照**：同一进程内交替三种阶段，各 30 秒，重复 3 轮：无写入；有写入；对照写入（同样频率、同样的
  RPC 解析、校验与响应，但存储层只做内存操作、不执行同步 SQLite 事务，仅探针构建可用）。
- **时间关联**：存储层记录每个事务同步执行的起止时间，server 用 `monitorEventLoopDelay` 记录主线程延迟；
  每个回显标注其往返区间是否与某个事务重叠。
- **结论规则**：被延迟的回显（超过同轮无写入阶段 p99）集中出现在与事务重叠的区间，或有写入阶段的延迟
  在每一轮都高于对照写入阶段（p < 0.01 且 p50 至少高 0.5 ms 或 p99 至少高 2 ms），即为 B；两种阶段在每一轮
  都与无写入阶段无差异才为 A；其余或测量不完整（流未达速率、订阅丢失、阶段受扰）为“未定”，
  须重跑或调查原因，不能视为 A，也不能归为调度噪声。
- **工作负载偏差**：少于 8 路有效流，或每路速率低于规定的 64 KiB/s，都记为工作负载偏差并写入报告。
  少于 8 路时 A 与 B 都只是暂定（PROVISIONAL）。8 路全部有效但降速时，A 仍为暂定：较轻负载下无阻塞
  不能排除规定负载下的阻塞；B 则成立（报告为附带偏差的 B，不降级）：较轻负载下写入已推迟主线程，
  提高输出速率只会增加同步提交周围的主线程工作，效应不会在规定速率下消失。因此 8 × 16 KiB/s 的 B
  足以支持本决定。
- 各阶段最大延迟与绝对值原样记录，只作观察，不单独作为失败条件。

- `cd5447a`：三轮有写入阶段均与对照写入无差异（p 0.999 / 0.447 / 0.9996），延迟回显不集中于与事务重叠的往返；
  第 3 轮对照阶段与无写入阶段有差异（p50 +0.63 ms、p99 +13.9 ms）。
- `673bb6c`：三轮有写入阶段均与对照写入无差异（p 0.020 / 0.557 / 0.999），延迟回显不集中于事务；
  第 2 轮有写入与对照阶段都比无写入高约同样幅度（p50 +0.39 / +0.44 ms、p99 +4.5 / +5.6 ms）。
- 事务 p99 约 3 ms，已移出主线程；事件循环延迟超过无写入 p99 的窗口：有写入与对照相当（88 / 89、92 / 111，均为 900 窗口中）。

两次探针结论均为“未定”：B 的两条条件都不成立，但 A 要求每轮两种写入阶段都与无写入阶段无差异，各有一轮不满足。
该差异在有写入与对照阶段同样出现，与主机负载无关且在阶段内平稳分布，归因于主线程上写入请求路径本身
（约 0.3–0.6 ms），不是数据库；另由 #107 跟踪。用户于 2026-10-16 据此确认 B 有效，#106 合入后关闭 #96。
该决定取代收尾原定的判定标准：按结论规则，“未定”须重跑或调查，降速下的 A 也只是暂定，
F-D6B 的收尾本应等到重跑得出明确结论；现以用户决定为准，不再为收尾重跑。
若 #103 修复后单个 worker 能承受规定速率，另以 8 × 64 KiB/s 运行一次作为规定负载下的确认。

未选：A（主线程同步调用；探针在 Linux 上测得写入阻塞主线程）；C（独立数据库进程，无对应需求）。

### D8. tab/run（选 A）

Tab：属于 task 的持久记录（名称、启动配方 = 可执行文件与参数或默认登录 shell、cwd = 入口目录或某挂载）。
Run：tab 的一次 PTY 实例（runId、启动时的 workspace revision 与挂载映射、开始/结束时间、退出码或结束原因）。
`tab create` 默认立即启动首个 run；`tab reopen` 用记录的配方新建 run；`tab stop` 停当前 run；`tab close`
仅在无存活 run 时删除记录。M0 的 `terminal create` 保留，产生不属于 tab 的 run，同样记录并适用重启语义。
不保存环境变量，只注入 `COVE_TASK_ID` 等少量标识。活动分类与 agent 状态不在 M1。
未选：B（无 tab，无法表达重开同一逻辑终端）；C（不存启动配方，重开 agent 需重输命令）。

T4 落实的细节：

- **标识注入（#120）**：tab 的每个 run（create 与 reopen）注入 `COVE_TASK_ID` 与 `COVE_TAB_ID`，只此两个。
  server 在 `domain/tabs.ts` 的 `coveRunEnvironment` 算出它们，经 pipe spawn 参数中有上限的 `env` 传给 worker
  （`SpawnEnvSchema`：封闭对象，只允许这两个键，值为 1–128 个可打印 ASCII 字符，未知键、空值、超长或控制字符
  均为 schema 错误）；worker 把它们设在自身继承的环境之上，并删除 spawn 未给出的同名键，因此在 Cove tab 中启动的
  server 不会把那个 tab 的标识传给自己的 run。`terminal create` 的 run 不属于 tab，不注入任何标识（继承来的
  也删除）；客户端不能经 `terminal.create` 传 `env`。标识不另外保存（run 记录本来就有 task 与 tab），也不写入日志。
  不用 `/usr/bin/env` 包装命令。
- **登录 shell**：配方 `shell` 在每次启动时取 server 用户的登录 shell（passwd 条目，其次 `$SHELL`，再次
  `/bin/sh`），以 `-l` 启动。
- **cwd**：入口目录，或一个记录为 ready 的挂载的真实路径；挂载已移除为 `MOUNT_NOT_FOUND`，未 ready 为
  `INVALID_ARGUMENT`。
- **一次只有一个未结束的 run**：tab 有 starting/running 的 run（含 worker 失联而无法核实的 run，失联不是退出）时，
  `tab reopen` 与 `tab close` 以 `LIVE_RUNS_PRESENT` 拒绝并列出这些 run。已归档 task 的 tab 不能新建或重开
  （`TASK_ARCHIVED`），停止与删除仍允许。
- **启动记录先于 spawn**：`tab create`（默认启动）与 `tab reopen` 在一个存储事务中复查回执、检查 tab 与 task、
  以 starting 记下 run 及其快照（task、workspace revision、cwd、全部挂载的名称/来源/真实路径）并写入 accepted
  回执，提交后才发 spawn。worker 明确拒绝 spawn 时删除该 run，tab 指回上一个 run（首个 run 被拒时 tab 保留且无
  run，操作为 failed 并在结果中给出 tab）；runtime 同时退役该 run，它不再列为终端，也不占 run 名额
  （[终端架构 3.6](../terminal-architecture.md)）。`tab stop` 的回执与 `terminal stop` 相同，看到退出事实后才 succeeded。
- **run ID 跨实例唯一且不重发**：新实例的 `run-N` 从本 server 发出过的最大 N 之后继续，取 run 记录与操作回执中
  run ID 的最大值：被拒的启动不留 run 记录，但其 failed 回执仍给出 run ID，所以重启后不会再把它发给新 run，
  CLI 按 run ID 固定的 `--run` 也不会匹配到别的 run；`tab runs` 可按 run ID 分页。回执目前从不删除；将来的回执清理
  必须先把被清理的最大 run 编号保存为计数器（届时再加 migration；现在两处已足够，不需要 schema 变更）。
- **供 T5 的查询**：`liveRunsUsing(store, runtime, path)` 返回没有结束记录、且启动 cwd 或挂载快照中的路径等于
  `path` 或位于其下的 run（按真实路径比较，含 `terminal create` 的 run）；registry 已观测到退出的不算。

### D9. 重启后的 run 显示（选 A）

启动时把属于旧 relayInstanceId、且无退出记录的 run 标为“会话中断”（生命周期 interrupted、可核实性
unverifiable，附旧实例 ID 与最后观测时间），说明其派生进程是否退出未核实；不探测旧 PID。
`cove server start` 前台进程收到停止信号时，先打印将受影响的存活 run 清单（来自库），再结束；不另做导出文件。
未选：B（探测旧 PID，PID 复用使结果不可靠）；C（显示为已退出，违反“不伪造退出”）。

### D10. 托管 worktree 的删除（选 B，加风险确认）

移除挂载时可选删除托管 worktree，**分支始终保留**。

- **唯一的硬拒绝**：有存活 run 在使用它（cwd 或挂载映射落在它下面）。拒绝时列出这些 run。
  托管 worktree 不能被其他 task 以 checkout 方式挂载（见 D2），因此不存在跨 workspace 的引用。
- **简单的风险确认**：删除请求必须带布尔值 `confirmed: true`，由领域操作在 RPC 层检查，所有客户端走同一操作；
  没有确认则不删除任何东西。CLI 提示这是有风险、不可撤销的删除，未提交和未跟踪的改动会丢失，
  交互时要求 y/N 确认，脚本中用 `--yes`。
- **允许删除有改动的 worktree**：确认后用 `git worktree remove --force` 删除，包括未提交和未跟踪的改动。
- 未选：A（不删除，托管目录累积）；C（同时删分支，依赖远端状态判断，误删风险高）。
  checkout 挂载与外部 worktree 在任何情况下都不删除。
