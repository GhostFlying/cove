## 交付范围

在 macOS/Linux 上，同一个独立 server 与 `cove` CLI 完成本地 task/workspace 闭环：

1. **持久 server 身份与存储**：server 使用 better-sqlite3 的本地 SQLite 库保存业务记录；
   `serverId` 跨重启不变，`relayInstanceId` 每次启动新建。同一数据目录只允许一个 server。
   写操作的 operation 记录持久化，重启后同一 operationId 仍去重、不重做。
2. **Repo 注册**：在本机注册任意路径的 Git clone，校验并规范化路径；注册不导入它已有的 worktree。
3. **Task 与 workspace**：一个 task 恰好一个 workspace，一个 workspace 一个入口目录（单仓也有）。
   一次 `task create` 可配置多个挂载，创建后可继续添加或移除挂载；task 可归档/取消归档。
4. **两种挂载来源**：`checkout`（已注册 clone 或它已有的 worktree，Cove 不拥有目录）与
   `worktree`（Cove 在 workspace 目录内新建并管理的 Git worktree）。
5. **多仓准备的逐仓结果**：部分失败时保留已完成的挂载，失败挂载可重试或移除，不把部分成功显示为完成。
6. **转到独立 worktree**：把一个 checkout 挂载换成新的托管 worktree，workspace revision 加一，
   旧 run 保留原绑定（范围见决策 D3）。
7. **Tab 与 run**：tab 是 task 下持久的逻辑终端记录，run 是它的一次 PTY 运行实例；
   默认 cwd 为 workspace 入口目录；停止、手动重开（新 runId）、查看历史 run。终端链路沿用 M0。
8. **重启语义**：server 正常停止或崩溃后重启，task/workspace/挂载/tab/run 记录保留；
   旧实例的 run 显示为会话中断且不可核实，不显示为存活，不自动重开或重跑任何命令。
9. **CLI 完整操作**：以上每项能力都有 `cove` 子命令与 JSON 输出，经同一 HTTP RPC 领域方法执行；
   包括本机初始化与 `workspaceRoot` 设置。

M0 已合入的终端链路（protocol、terminal-engine、terminal-worker、client、terminal-web、
harness）保持现状。M1 只在 run 的创建与记录处接入，不重构终端恢复、focus 或流控。
M0 测试 harness 继续作为交互载体：tab 的 run 也是普通终端 run，可在 harness 中 attach。

### 明确不做

- 跨主机迁移、rollout 复制、跨主机 repo 映射表（M4）；远程接入、配对、设备授权、tsnet、服务安装与开机自启（M2）。
- Electron、RN/WebView、Web App 及任何新的 GUI（M3 与二期）；业务事件 WebSocket 订阅（M3 有 GUI 时再加，
  M1 的资源都带 revision，CLI 按需读取）。
- 独立 PTY keeper、终端画面/恢复基线/scrollback 落盘、重启后接管旧 PTY。
- 普通目录（`directory`）挂载；转 worktree 时携带未提交改动（见 D3）。
- 普通终端活动分类（执行中/近期/闲置）与 shell integration、agent 识别与 agent 工作状态、agent hook。
- 定时任务、chat、Shepherd、managed agent。
- 计划重启前导出单独的 tab 清单文件：tab/run 日常持久化在库中，`cove tab list` 即是清单（见 D9）。
- 不新增 npm package；领域代码是 `apps/server` 的内部模块（[工程 §1](../engineering-plan.md#1-已确认单仓库建议按部署入口和真实依赖边界组织)）。

## 验收场景

每个场景是一个启动编译产物（`cove-server`、`cove` CLI）的自动化测试，在 macOS 与 Ubuntu CI 上运行，
结果只有通过或失败。测试在临时目录中用 `git init` 建临时仓库，使用独立的临时 Cove 数据目录与
workspace 根目录，不触碰真实 `~/.cove` 或用户仓库。CI 绿灯就是证据，不另行封存。
场景 S6、S9 的具体断言取决于 D3、D10 的用户选择；下表按推荐选项书写。

| ID  | 场景                                                                                                                                                                                                                                                                                                 |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | 注册 repo：经符号链接或尾部斜杠给出的路径被规范化为真实 clone 顶层；同一 clone 重复注册、非 Git 目录、bare 仓库被明确拒绝；该 clone 已有的外部 worktree 不出现在 task 列表；`repo remove` 不改动目录。                                                                                               |
| S2  | 调查 task 使用共享 checkout：不创建分支或 worktree；workspace 入口目录存在并能经入口看到来源的未提交改动；两个 task 挂载同一 checkout 时双方都显示共享关系；归档并移除挂载后来源目录内容不变。                                                                                                       |
| S3  | 一次 `task create` 配置三个挂载（两个仓库各建新 worktree，另一个用已有 checkout）：得到一个 task、一个 workspace，每个挂载显示各自的仓库、分支与基准提交；两个 worktree 位于该 workspace 目录内，来源 clone 的分支与工作区不变。                                                                     |
| S4  | 多仓部分失败：第二个仓库的目标分支已存在导致失败，操作终态为 failed 并逐仓列出结果；第一个 worktree 保留且已记录，没有 run 被自动启动；用同一 operationId 重发返回原记录、不再执行；修正后重试失败挂载成功。                                                                                         |
| S5  | Tab 与 run：在 task 中创建 tab，run 的 cwd 是 workspace 入口目录并能列出各挂载；run 退出后记录退出码，tab 保留；`tab reopen` 产生新 runId，旧 run 仍在历史中；在 harness/客户端断开期间 run 继续运行。                                                                                               |
| S6  | 转到独立 worktree：来源有未提交改动时，有存活 run 则拒绝转换；结束 run 后从所选提交创建 worktree，revision 加一；来源的未提交改动原样保留在来源；旧 run 记录仍指向原 checkout，新 run 位于新 worktree。                                                                                              |
| S7  | Server 重启：分别以正常停止与 `kill -9` 结束 server（各有一个运行中的 tab），重启后 serverId 不变、relayInstanceId 改变；记录全部保留；正常停止时旧 run 记为随 server 停止而结束，`kill -9` 时显示会话中断/不可核实，都不显示为存活；启动命令的标记文件数量不变（未重跑）；`tab reopen` 后标记加一。 |
| S8  | 操作中途崩溃：worktree 创建期间（由临时仓库的 `post-checkout` hook 阻塞）`kill -9` server；重启后该操作经核实为 succeeded 或 requires_attention，不会自动再次执行；按提示继续或移除后状态一致，无重复 worktree 或分支。                                                                              |
| S9  | 资源所有权：外部删除托管 worktree 目录后 task 仍在、挂载显示缺失且不被重建；在 workspace 根目录下用 git 直接建的 worktree 不出现；删除托管 worktree 在有未提交改动或存活 run 时被拒绝，满足条件后删除目录并保留分支；移除 checkout 挂载从不删除来源。                                                |
| S10 | 存储守卫与设置：同一数据目录启动第二个 server 被明确拒绝且不影响第一个；schema 版本高于当前构建的数据库被拒绝打开且文件不变；`cove server init` 与 `workspaceRoot` 设置经 CLI 完成，修改只影响之后新建的 workspace。                                                                                 |

另需用户做约一小时的真实使用试用，检验自动化覆盖不到的真实 Git/agent 行为：

- 注册两个真实仓库；创建调查 task 挂载已有 checkout，在 workspace 入口启动 Claude Code、Codex 或 TraeX，
  让 agent 读取并在挂载中执行 git 命令，确认 agent 能经入口访问真实目录。
- 创建两仓 task（各建新 worktree），在 agent 中分别修改、提交；确认分支和提交只出现在对应 worktree。
- 将调查 task 转到独立 worktree，确认旧 tab 仍指向原位置，新 tab 在新 worktree。
- 有 agent 运行时重启 server：确认显示为会话中断而非存活；手动重开 tab 后用 agent 自身的 resume 继续
  （是否能续上是 agent 的行为，只作观察，不是 Cove 的验收）。
- 通过 harness attach tab 的 run，确认 M0 终端链路在 task 场景中照常工作。

发现的问题修复后再提交阶段 review。

## 待用户决策

以下决策阻塞 M1 实施，需在批准计划时逐项确认或改选。已确认的决策（SQLite + better-sqlite3、
一个 task 一个 workspace、统一可配置 workspace 根目录、agent 默认 cwd 为 workspace 入口、
列表只展示 Cove 记录、无 keeper、终端持久化方案 A、CLI 为完整操作入口）不在此重开。
Orca 对照来自本地 checkout（版本见文末“Orca 对照”）。

### D1. Workspace 根目录与目录布局

| 选项 | 内容                                                                                                                                       | 影响                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| A    | `<workspaceRoot>/<slug>-<短 ID>/<挂载名>`；slug 由 task 标题生成、创建时固定，之后改标题不改目录；挂载名默认取 repo 显示名，冲突时要求指定 | 路径可读，agent/终端里能看出是哪个任务；目录名只是记录，不从目录名反推身份          |
| B    | `<workspaceRoot>/<workspaceId>/<挂载名>`，只用不透明 ID                                                                                    | 永不冲突、实现最简单；人在终端和 agent 历史里难以分辨任务                           |
| C    | 按仓库分组 `<workspaceRoot>/<repo>/<task>`（类似 Orca 的按仓库布局）                                                                       | 与“每个 workspace 一个入口目录、多仓共处一个入口”冲突，多仓 task 需要另一层入口目录 |

托管 worktree 的默认分支名为 `cove/<slug>`（可用 `--branch` 覆盖），基准默认为来源 clone 当前 HEAD 的提交
（可用 `--base <ref>` 指定），**不隐式 fetch**；需要远端最新代码时由用户先 fetch 或显式指定 ref。
默认 `workspaceRoot` 为已建议的 `~/.cove/workspace`。

Orca 按 repo 名分组放置 worktree，同名仓库会共用目录；分支默认 `<git 用户名>/<名称>`，并会隐式 fetch。

**推荐 A**，并采用上述分支与基准默认值。

### D2. 已有 checkout 的引用方式与新 worktree 的放置

| 选项 | 内容                                                                                                                                                                                                                              | 影响                                                                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| A    | 托管 worktree 直接建在 `<入口>/<挂载名>`；checkout 挂载在 `<入口>/<挂载名>` 放一个指向真实路径的符号链接。入口路径在 workspace 生命周期内不变；替换某个挂载的绑定时，要求该 workspace 没有存活 run，然后替换该入口并递增 revision | 实现简单；agent 恒在同一 cwd，利于 agent 按 cwd 保存的会话续接；代价是换绑定前要先结束该 workspace 的 run |
| B    | 版本化入口 `<入口>/r<revision>/<挂载名>`，每个 run 的 cwd 为启动时的 revision 目录；换绑定不影响旧 run                                                                                                                            | 旧 run 永远看到原绑定；但 cwd 随 revision 变化，agent 按 cwd 的会话历史会分裂，目录层级也更深             |
| C    | 不给 checkout 建入口，只在 workspace 记录真实路径；只有 checkout 的 workspace 直接以 checkout 为 cwd                                                                                                                              | 无符号链接问题；违背已确认的“每个 workspace 都有入口、默认 cwd 为入口”，多仓时 agent 看不到其他仓库       |

checkout 挂载只能引用已注册 clone 本身，或与它共享同一 Git common dir 的已有 worktree（显式给出路径）；
被选中的已有 worktree 不因此成为 Cove 可删除的资源。

Orca 的多仓 task 把已有链接 worktree 用 `git worktree move` 移进根目录（移动前做存活检查），
主 checkout 则留在根目录外，agent 从根目录看不到；Cove 已确认不移动用户目录。

**推荐 A**。符号链接对 agent 目录授权、Git 和文件监听的影响由 S2/S5 与真实试用验证；试用若发现阻塞问题再评估 B。

### D3. 转到独立 worktree 的范围与来源有改动时的策略

| 选项 | 内容                                                                                                                                | 影响                                                                      |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| A    | M1 不做转换；需要隔离时新建 task                                                                                                    | 最省事；但设计 §3 的核心工作流和“同一 task 可更换工作位置”要推迟          |
| B    | 只支持“从提交开始、不带改动”：展示来源的已暂存/未暂存/未跟踪改动，原样留在来源，不 stash/reset/切换来源分支；来源干净时就是普通转换 | 覆盖调查转开发的主路径，行为清楚；需要带走改动的用户自己提交或手动复制    |
| C    | B 加上“携带选定改动”（暂存、未暂存、未跟踪、权限与二进制）                                                                          | 功能完整；需要快照一致性检测和多种文件状态处理，复杂度接近迁移，M1 风险大 |

**推荐 B**，列为 T5 单独切片；若进度紧张可先合入 T0–T4 再决定是否保留 T5。

### D4. 共享 checkout 的多写入者限制

| 选项 | 内容                                                               | 影响                                                                 |
| ---- | ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| A    | 不加锁，只展示共享关系：`task get`/`mount` 列出共用同一目录的 task | 与设计 §13.2 的建议一致；Cove 锁本就约束不了外部编辑器，不给虚假保证 |
| B    | 每个 checkout 同时只允许一个 task 挂载为可写，其他为“只读意图”     | 需要定义只读意图且无法真正强制，容易被理解成已隔离                   |
| C    | 挂载同一 checkout 前强制确认（CLI 需 `--shared`）                  | 多一步交互，脚本需多传参数；与 A 组合也可                            |

**推荐 A**（若希望更显眼，可叠加 C 的确认参数）。

### D5. 数据库位置、schema 与迁移方式

| 选项 | 内容                                                                                                                                                                                                                                                                                              | 影响                                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| A    | 数据目录 `~/.cove`（可用 `COVE_HOME` / `--home` 覆盖，测试用临时目录），库在 `~/.cove/server/cove.db`，目录权限 0700；手写顺序 SQL 迁移、以 `PRAGMA user_version` 记版本，启动时在一个事务里前进迁移，迁移前用 `VACUUM INTO` 留备份；库版本高于构建时拒绝启动且不改文件；WAL + `synchronous=FULL` | 无 ORM 依赖，迁移可审阅；首个正式版前也保留升级路径  |
| B    | 同 A 的位置，用 Drizzle/Kysely 等查询构建器及其迁移工具                                                                                                                                                                                                                                           | 类型化查询；新增依赖与生成步骤，迁移文件格式绑定工具 |
| C    | 首个正式版前不写迁移，schema 变化时拒绝启动并要求重建库                                                                                                                                                                                                                                           | 最省事；试用期间用户真实 task 记录会因升级丢失       |

位置备选：Linux 用 `$XDG_STATE_HOME/cove`、macOS 用 `~/Library/Application Support/Cove`；

Orca 用单个 JSON 文件整体重写，迁移靠加载时归一化，没有编号迁移。

**推荐 A**。持久 serverId 存在库内；数据库 schema 版本与协议版本、配置 schemaVersion 互相独立。

### D6. Server 单进程还是数据库放在 worker thread

| 选项 | 内容                                                                                                                                                  | 影响                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| A    | M1 在 runtime 主线程直接同步调用 better-sqlite3，每个业务操作一个短事务；Git 等外部命令异步子进程执行                                                 | 最简单；M1 写入频率低（每次用户操作几条记录），终端热路径在 worker 子进程，不经数据库 |
| B    | 按 [Server 架构 §11.1](../server-architecture.md#111-node-驱动与执行位置已选择-better-sqlite3执行位置待定) 的建议，专用数据库 worker thread、有界队列 | 主事件循环不受磁盘提交阻塞；多一层消息与生命周期管理，M1 负载下收益难以测出           |
| C    | 独立数据库进程                                                                                                                                        | 进程边界与故障处理成本最高，无对应需求                                                |

**推荐 A**：存储模块只暴露“完整业务操作”的函数，不跨调用拆开事务，日后移入 worker 只改这一层。
M4 容量验收时测量事务耗时，超出预算再改 B。

### D7. CLI bootstrap、安装目录与 server 生命周期

| 选项 | 内容                                                                                                                                                                                                                                                                               | 影响                                                                |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| A    | 沿用 M0：`cove server start` 前台运行；新增 `cove server init`（服务未运行时初始化数据目录、serverId、`workspaceRoot`），`start` 在未初始化时按默认值初始化；单实例由数据库独占锁保证，崩溃留下的 rendezvous 由新取得锁的 server 安全替换；从仓库构建产物运行，稳定安装目录留给 M2 | 不提前做部署；试用时 server 在一个终端或 tmux 中运行                |
| B    | A 加 `cove server start --detach` 与 `cove server stop`（脱离终端、日志写入数据目录）                                                                                                                                                                                              | 试用更方便；后台化与日志轮转本是 M2 的部署内容，提前部分实现        |

不跑在正在开发的 worktree 里。

### D8. “tab/run”的具体含义

| 选项 | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                | 影响                                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| A    | Tab：属于 task 的持久记录（名称、启动配方 = 可执行文件与参数或默认登录 shell、cwd = 入口目录或某挂载）。Run：tab 的一次 PTY 实例（runId、启动时的 workspace revision 与挂载映射、开始/结束时间、退出码或结束原因）。`tab create` 默认立即启动首个 run；`tab reopen` 用记录的配方新建 run；`tab stop` 停当前 run；`tab close` 仅在无存活 run 时删除记录。M0 的 `terminal create` 保留，产生不属于 tab 的 run，同样记录并适用重启语义 | 与 [终端设计 §12.1](../terminal-architecture.md#121-逻辑-tab-与运行实例分开) 一致；不保存环境变量，只注入 `COVE_TASK_ID` 等少量标识 |
| B    | 不引入 tab，run 直接属于 task                                                                                                                                                                                                                                                                                                                                                                                                       | 少一层；无法表达“同一个逻辑终端重开”，与已确认的 tab 记录与手动重开冲突                                                             |
| C    | A，但 tab 不保存启动配方，重开总是启动 shell                                                                                                                                                                                                                                                                                                                                                                                        | 更简单；重开 agent 需要用户每次重输命令                                                                                             |

**推荐 A**。活动分类与 agent 状态不在 M1。

### D9. 随 server 结束的 run 在重启后如何显示

| 选项 | 内容                                                                                                                                                                                     | 影响                                                                   |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| A    | 启动时把属于旧 relayInstanceId、且无退出记录的 run 标为“会话中断”（生命周期 interrupted、可核实性 unverifiable，附旧实例 ID 与最后观测时间），说明其派生进程是否退出未核实；不探测旧 PID | 不给虚假结论；用户看到的是事实边界。PID 可能被复用，探测结果本就不可靠 |
| B    | A 加探测旧 PID 是否存在（结合进程启动时间），显示“原进程可能仍在运行”                                                                                                                    | 能提示 `nohup` 等残留进程；需要平台相关的进程查询，误判仍可能发生      |
| C    | 直接显示为“已退出”                                                                                                                                                                       | 违反“不伪造退出”的已确认规则，不可选                                   |

另外，`cove server start` 前台进程收到停止信号时，先打印将受影响的存活 run 清单（来自库），再结束；
M1 不另做导出文件。Orca 有 daemon 保活；daemon 死后回放落盘画面并自动 spawn 新 shell，Cove 已确认不这样做。

**推荐 A**。

### D10. 托管 worktree 的删除

| 选项 | 内容                                                                                                                                  | 影响                                                     |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| A    | M1 不删除目录：移除挂载只解除关系，托管 worktree 留在磁盘，由用户手动 `git worktree remove`                                           | 最安全；托管目录会累积，且手动删除后记录变为“缺失”       |
| B    | 移除挂载时可选删除托管 worktree：要求无存活 run、工作区干净（含未跟踪文件），用 `git worktree remove`（不加 `--force`），**保留分支** | 保留分支即保留全部提交，只有未提交内容需要守卫，规则简单 |
| C    | B 再加删除分支（要求分支已合入或已推送）                                                                                              | 更彻底；“已推送/已合入”的判断依赖远端状态，误删风险更高  |

Orca 删除时默认要求干净，分支仅在已合入或已发布时删除。

**推荐 B**。checkout 挂载与外部 worktree 在任何选项下都不删除。
