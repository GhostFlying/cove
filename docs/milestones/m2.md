## 交付范围

在 macOS/Linux 上：

1. **本地服务部署**（M1 D7 留下的部分）：`cove server install` 把一次构建的完整运行闭包（含固定版本的 Node 与原生模块）
   装到稳定的版本化目录，并注册为后台服务；服务脱离启动它的 shell、SSH 会话和任何客户端，崩溃后由服务管理器拉起。
   注销后与登录前是否运行按平台不同：Linux 在 linger 下都运行；macOS 用 LaunchAgent，注销时停止、登录时自动启动（D2，用户已决定）。
   安装新版本不会替换正在运行的 server，切换要用户显式重启；回退只限于与数据库 schema 兼容的版本（D1、D2）。
2. **部署与重启影响可检查**：`cove server status` 报告已安装版本、正在运行的 build、服务状态、上次启动原因（手动或崩溃后拉起）
   以及是否有已安装但尚未生效的版本。`cove server restart`/`upgrade` 先列出将被中断的存活 run，确认后才执行。
   重启后 run 显示为会话中断（M1 D9），不自动重跑。
3. **设备配对与撤销**：server 签发一次性邀请；按下文的配对状态机兑换与领取，响应丢失后可凭申请密钥重新领取；
   兑换后得到每设备独立、可撤销的长期 token。撤销立即关闭该设备的活动连接并释放其控制权（D4–D8）。
4. **SSH 入口**：远程 CLI 用系统 `ssh` 把客户端 loopback 上的端口转发到执行主机的 loopback 入口，并验证 SSH host key（D3、D11）。
5. **系统 Tailscale 入口**：server 只额外监听本机的 Tailscale 地址；该入口不可用时不扩大监听范围（D9）。
6. **独立 tsnet 入口**：Go 模块 `native/tailscale` 构建 `cove-tsnet`，作为独立 Tailnet 节点接受连接，经同机受控 IPC 转交 Node；
   节点状态持久，与系统 tailscaled 互不影响（D10）。
7. **切入口保持身份**：客户端按 serverId 记录一台 server 及其多个已验证入口；换入口时先核实通道对端与 serverId，再发送 token；
   task、run 与终端订阅是同一份，不重复启动服务或建立新身份。
8. **CLI 作为远程 operator**：全部业务命令可用 `--server <别名>` 指向远程 server，走与本机相同的 RPC 领域方法；
   入口由 `--via` 或该别名登记的默认入口决定；远程模式下路径参数必须是执行主机上的绝对路径。
   安装、服务管理与启停仍是本机 bootstrap 边界（D11）。
9. **操作记录保存期限（#97，用户已于 2026-10-21 决定）**：已结束（succeeded/failed/cancelled）的操作记录在结束后保存 30 天；
   未结束的（含 requires_attention）从不自动清理；重发已过期的 operationId 返回明确的过期错误，绝不重新执行（实现方式见 D13）。

M0/M1 已合入的终端链路与领域保持现状。M2 只在入口、认证与部署处接入，不重构恢复、focus 或流控。

### 明确不做

- Electron、RN/WebView 客户端与其凭据存储、移动端网络验证（M3）；Web App 与浏览器会话、Tailscale Serve HTTPS（二期）。
- 跨主机迁移与文件传输（M4）；发行安装器、签名、公证、自动更新与发布产物（M4）；100 终端容量验收（M4）。
- 由客户端把 server 推送部署到远程主机：M2 中每台主机在本机用自己的 CLI 安装。
- 应用层 E2EE、Cove 自有 TLS/CA、JWT 或客户端证书（[Server 架构 §9.4](../server-architecture.md#94-安全通道与设备授权已选择-sshtailscale) 已决定不做）。
- 裸 LAN/公网监听；自动修改防火墙或系统 tailscaled 配置；移动端内嵌 Tailscale。
- 短数字配对码、二维码（邀请是可复制的高熵字符串，二维码不是必要条件）。
- 独立 PTY keeper；server 重启后保留 PTY。业务事件 WebSocket 订阅（随 M3 的 GUI）。
- 跨入口的自动选路与失败后自动换入口：读写命令都不自动换入口（只有用户在 D11 选 B 时，才放开有界的只读回退）。
- 数据库自动降级，以及回退到不兼容 schema 的旧版本（D1）。
- 不新增 npm package；认证与入口代码是 `apps/server` 与 `apps/cli` 的内部模块。

## 威胁模型与认证边界

M2 是 Cove 的认证边界。受信任的是通过认证的单一所有者：主机上的同一 OS 用户（能读取数据目录中的本机秘密）
与每台已配对设备。按 AGENTS.md「Trust the authenticated owner」，不防范所有者攻击自己。
已配对设备可以经终端以该用户身份在主机上执行任意命令，因此设备之间的权限分级不构成隔离（D7）。

需要防范的对象：

| 对象                                                   | 能做什么                                    | M2 的边界                                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 同一 Tailnet 的其他节点（共享 Tailnet、他人设备、tag） | 连到系统 Tailscale 与 tsnet 入口            | 没有设备 token 只能完成版本握手；不按来源属于 100.64.0.0/10 判断可信，Tailscale 用户或节点身份不替代 Cove 授权                |
| 同一主机上的其他 OS 用户（多用户 devbox）              | 连 loopback 端口，读取权限宽松的文件        | 秘密文件 0600、目录 0700；服务单元、命令行参数、环境变量与日志都不含 token、邀请 secret 或 auth key                           |
| 客户端所在网络上的其他主机                             | 连到客户端为 SSH 隧道开的本地端口           | 本地转发端固定绑定 `127.0.0.1`，并在命令行覆盖用户配置中的 `GatewayPorts`（T2、S6）                                           |
| 拿到邀请字符串的第三方（剪贴板、聊天记录）             | 抢先兑换                                    | 短有效期、单次兑换、可取消、每邀请与全局的尝试次数有限；兑换后 secret 失效，重新领取只认申请密钥                              |
| 丢失或被盗的设备                                       | 持有长期 token                              | 撤销后立即失去全部连接与访问，包括查询自己过去的操作（D8）                                                                    |
| 所有者浏览器中的恶意网页                               | 跨站请求、DNS rebinding 到 loopback/Tailnet | 每个入口都做 M0 的 Host/Origin 校验；token 不进 URL 或 cookie                                                                 |
| 通道中间人                                             | 冒充 server 骗取 token                      | SSH host key 与 WireGuard 节点密钥保证对端；客户端在发送 token 前核实通道对端与 serverId；经 subnet router/跳板的明文段不保证 |
| 第三方数据                                             | `ssh`、`tailscale` 的输出与节点名           | 按不可信输入解析并限界，不拼进 shell 命令                                                                                     |

不在范围：主机 OS 账户或 root 已被攻破；Tailscale 控制面或 SSH 账户被攻破（Cove 撤销不等于撤销 SSH/Tailscale 权限）。

认证前可达的面，逐项在 S11 中验证：

- `/bootstrap` 握手：只返回 bootstrap/协议版本、build、serverId 与 relayInstanceId，供客户端在发送 token 前核对；
  不返回 task、路径、设备或终端信息。serverId 是标识，不是身份证明。
- 终端 WebSocket 在首帧认证之前的阶段（沿用 M0 的首帧期限与未认证连接预算）。
- 配对监听，只在下节规定的开放条件下存在。
- `cove-tsnet` 与 Node 之间的 Unix socket（0700 目录，只有同一 OS 用户可连）。
- 所有入口都有界：未认证连接数、请求体、首帧期限、配对尝试次数。认证失败不区分“设备不存在”与“secret 错误”，
  比较用常数时间。日志只记 deviceId 与入口种类。

## 配对状态机

一次配对从用户看是这样的（以笔记本配对 devbox 为例）：

1. 在 devbox 上执行 `cove auth invite create`（或在已配对设备上远程创建）。server 记录邀请，打开配对监听，
   输出一行邀请字符串，内含 serverId、入口、配对端口、一次性 secret 与到期时间（默认 10 分钟）。
2. 把这行字符串复制到笔记本，执行 `cove remote add devbox --invite '<字符串>'`。CLI 先把邀请和自己生成的申请密钥写入本机配对待定文件。
3. CLI 经邀请中的入口（如 SSH）连到配对监听，先核实通道对端（SSH host key 或 Tailscale 节点），再提交 secret 与申请密钥。
4. server 在一个事务内完成兑换：作废 secret，建设备，生成长期 token，只保存其哈希；把 token 返回给 CLI。
5. CLI 把 token 写入凭据文件，用它发一次认证请求；server 收到后把设备标为已领取，没有其他待处理邀请时关闭配对监听。
   CLI 删除待定文件，配对完成。之后笔记本用 `--server devbox` 直接连接，不再需要邀请。
6. 如果第 4 步的响应在路上丢了：再次执行同一条 `cove remote add`，CLI 读到待定文件，凭申请密钥重新领取，得到同一设备的新 token。
   超过领取期限仍未领取时，server 自动撤销这个从未用过的设备，用户需要重新创建邀请。

按 D6 的推荐 A 描述；D6 选其他选项时本节随之修改。邀请与设备状态都存在 SQLite，server 重启后原样恢复，期限按墙钟计算。

| 邀请状态                         | 进入条件                                                                                                                               | 离开                                                                                            |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `open`                           | 签发（本机 CLI 或已配对设备）                                                                                                          | 兑换 → `redeemed`；取消 → `cancelled`；到期 → `expired`；错误 secret 达到上限 → `cancelled`     |
| `redeemed`                       | **兑换提交**：一个事务内校验 secret 并作废它，新建设备（`pending-claim`），保存 token 与申请密钥的哈希，记录领取期限（兑换后 10 分钟） | 新 token 首次认证成功 → `claimed`；领取期限已过 → `claim-expired`；设备被撤销 → `claim-revoked` |
| `claimed`                        | **凭据已领取**：设备转为 `active`                                                                                                      | 终态                                                                                            |
| `claim-expired`、`claim-revoked` | 设备一直未领取（自动撤销，原因 unclaimed），或领取前被撤销                                                                             | 终态；客户端需要新邀请                                                                          |
| `cancelled`、`expired`           | 见上                                                                                                                                   | 终态                                                                                            |

- **监听开放条件**：至少有一个 `open` 邀请，或一个领取期限未过的 `redeemed` 邀请。最后一个这样的邀请离开这两个状态时
  关闭监听（**监听关闭**），不影响业务端口、已连接设备与 PTY。这是把已确认约束中的“已兑换”细化为“已兑换且已领取，或领取期限已过”，
  需要用户在 D6 确认。
- **领取路径**：兑换响应丢失后，客户端带同一 inviteId 与申请密钥重新连接配对监听。邀请为 `redeemed`、领取期限未过且设备未被撤销时，
  server 为同一设备重新签发 token（替换哈希，此前未送达的 token 失效），返回同一 deviceId。secret 已作废，重试只凭申请密钥
  （常数时间比较），计入该邀请的尝试上限。其他状态一律拒绝，错误与无效申请相同（`INVITATION_UNAVAILABLE`），不透露邀请是否存在。
- **客户端**：`cove remote add` 兑换前把邀请与申请密钥写入 0600 的本机配对待定文件；拿到 token 后先写入凭据文件，
  再发一次认证请求完成领取，成功后删除待定文件。重新运行 `cove remote add` 时，如有待定文件则走领取路径。
- **重启**：兑换事务已提交而响应未送达时 server 重启，启动后按开放条件重新打开配对监听，领取期限内的重试照常成功（S12）。

## 秘密与操作记录的分界

现有写操作会保存规范化参数、指纹与结果，CLI 也会保存待定请求，秘密不能沿用这些机制。T0 在方法表中为每个方法声明秘密字段，
由分派层与 CLI 统一执行：

1. **含秘密的方法**：`auth.invite.create`（输出邀请 secret）、`auth.device.rotate`（输出新 token）、`server.tsnet.login`（输入 auth key）。
   配对兑换与领取走配对监听，不是 RPC 操作，不建操作记录。
2. **输入秘密**不进入操作指纹、规范化参数与操作记录；auth key 经 stdin 交给 `cove-tsnet` 后即丢弃。
3. **输出秘密**只出现在这一次实时响应中；操作记录的 result 只保存非秘密部分（inviteId、到期时间、deviceId）。
   `operation get` 与同一 operationId 的重发返回该记录，不含秘密，并注明秘密只交付一次。
4. **丢失的一次性秘密不能取回**，恢复是新的显式操作：邀请——`auth invite cancel` 后重新创建；token 轮换——两阶段，
   新 token 首次认证成功前旧 token 仍有效，响应丢失时用旧 token 再次轮换，替换未领取的新 token；tsnet 登录——用
   `server tsnet status` 查看结果，必要时用新的 auth key 重新登录。
5. **CLI 待定记录**不保存秘密字段；有秘密输入的请求不能 `operation resend`，CLI 在本机拒绝并提示重新执行原命令。
6. 设备 token 与邀请 secret 在 server 端只以哈希存储；日志、错误与诊断不含任何秘密。有意保存秘密的位置只有客户端凭据文件
   （设备 token）与客户端配对待定文件（邀请 secret 与申请密钥，领取后删除），都是 0600。

## 验收场景

每个场景是启动编译产物（`cove-server`、`cove` CLI，以及 S9 的 `cove-tsnet`）的自动化测试，用临时数据目录与临时客户端目录，
不触碰真实 `~/.cove`、用户的服务单元、ssh 配置或 Tailnet。同一台机器上用两个客户端目录模拟两台设备。
需要丢弃响应时，由测试夹具中的转发代理在响应到达客户端前断开连接，不在 server 中加测试钩子。
“验证”一列说明能否在 CI 中执行；CI 执行不了的部分按[工程 §6.9](../engineering-plan.md#69-按比例验证与停滞处理2026-10-08-用户确认)

## 任务拆分

每个任务一个 PR，由独立 subagent 在各自 worktree 实现；每个 PR 带上自己负责的场景测试，测试放在 `apps/cli/tests/m2/`，
按 M1 的 `.suite.json` 方式登记。每个改变 tend 可见接口（CLI 命令、参数、退出码、JSON 输出）的 PR 同时更新

- **协议 schema、方法表、错误码、bootstrap 与客户端**：T0 唯一写入。T0 定义全部 M2 方法、错误码与每个方法的秘密字段，
  在 server 分派中为 `auth`、入口与服务状态建只返回 `CAPABILITY_UNAVAILABLE` 的初始模块，把认证结果作为主体（本机所有者或 deviceId）

### D2. 服务管理器与各平台的运行保证（平台已由用户决定；停止清理待用户决策）

用户于 2026-10-21 决定：macOS 用用户 LaunchAgent，接受注销时停止、登录时自动启动；Linux 用 systemd user unit 加 linger。
停止时的进程清理仍待用户决策。

两个平台都满足：脱离启动它的 shell、SSH 会话与任何客户端；崩溃后有限次数拉起，正常退出不拉起；`server status` 报告启动原因。

| 平台  | 服务单元                                                         | 运行保证                                                                                                                                                                                                                |
| ----- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux | systemd user unit，开启 linger                                   | 开机即运行，注销后继续运行。未开启 linger 时 CLI 报告并给出 `loginctl enable-linger` 命令，不自行 sudo；没有 systemd user 的主机（容器等）继续用 M1 的前台 `cove server start`                                          |
| macOS | 用户 LaunchAgent（`~/Library/LaunchAgents`，gui 域），不需要提权 | 用户登录后自动启动；**注销时停止**：server 与全部 PTY 结束，run 记为随 server 停止（stopped-with-server），不自动重跑；开机后用户登录前不运行。运行在用户的登录会话中，ssh-agent、钥匙串与 TCC 授权和用户平时的终端一致 |

未选（macOS）：系统 LaunchDaemon（开机即运行、注销不受影响，但安装、切换与卸载要 sudo，且不在登录会话中：没有 ssh-agent，
钥匙串与 TCC 访问不同）；两者都提供（两套单元与测试）。Cove 自行后台化（`start --detach`）没有崩溃拉起与可依赖的注销行为，也不采用。

**停止时的进程清理（待用户决策，只涉及 Linux）**：

| 选项 | 内容                                                                                                                                                | 影响                                                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| A    | systemd 默认 `KillMode=control-group`：停止或重启服务时结束 cgroup 内全部进程，包括用户在 Cove 终端里用 `nohup`/tmux 脱离的进程；重启影响说明中写明 | 停止后没有遗留进程；与前台运行时不同，脱离的进程也会被结束                         |
| B    | `KillMode=process`：只结束 server 主进程，其余进程由 server 自己的停止流程处理                                                                      | 脱离的进程得以保留；崩溃或强杀后可能留下无人管理的孤儿进程，systemd 也不再保证清理 |

**推荐 A**。macOS 的 LaunchAgent 结束 server 时，用户在终端里脱离的进程是否保留由 launchd 与进程会话决定，在 S1 的实机验证中记录实际行为。

Orca 不安装任何服务单元；daemon 是应用 fork 出的脱离子进程，没有开机自启或崩溃拉起。

### D6. 配对：兑换、领取与监听（待用户决策）

已确认：一次性邀请、短有效期、单次兑换、可取消、只在有效邀请期间开放配对监听、邀请含入口、serverId、高熵 secret 与有效期。
各选项共同的部分：配对监听用独立端口（D3），只在已启用的入口上开放；邀请字符串 `cove-invite:v1:<base64url>` 含 serverId、入口

兑换请求带客户端生成的申请密钥；每邀请 5 次错误后作废，另有全局速率上限。三个选项的区别是兑换响应丢失后怎样恢复：

| 选项 | 内容                                                                                                                                                                                         | 影响                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| A    | 按上文“配对状态机”：兑换提交后进入领取期限（10 分钟），期间配对监听保持开放；客户端凭申请密钥领取同一设备的新 token；新 token 首次认证成功即为领取，之后关闭监听；期限内未领取的设备自动撤销 | 唯一邀请的响应丢失也能恢复，server 重启后照常；把已确认约束中的“已兑换后关闭监听”细化为“已兑换且已领取或领取期限已过后关闭”，需用户确认 |
| B    | 兑换后立即关闭配对监听；领取改走业务端口上的一个未认证端点，只接受领取期限内带正确申请密钥的请求                                                                                             | 严格保持“兑换后关闭配对监听”；但业务端口多出一个认证前可达的端点，扩大了业务入口的未认证面                                              |
| C    | 不提供重试：兑换后立即关闭监听；响应丢失时该设备一直未领取，期限后自动撤销，用户重新创建邀请                                                                                                 | 最简单，监听与业务入口都不增加；响应丢失时用户要重新签发邀请                                                                            |

**推荐 A**。期限、次数与有效期是建议的默认值，可在批准时调整。

### D8. 撤销对活动连接的语义（待用户决策）

已确认：撤销同时失效活跃连接，不能只禁止下次登录。

| 选项 | 内容                                                                                                                                                                                                                                                                                                                                   | 影响                                                                                          |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| A    | 一个事务内标记设备撤销并取消它创建且未兑换的邀请；提交后拒绝它的新请求（`DEVICE_REVOKED`），以撤销原因关闭它的全部 WebSocket，释放它持有的终端控制权（epoch 前进，不 resize），丢弃尚未发出的响应；它已受理的操作照常执行完毕，记录可由其他设备查询；它启动的 run 继续运行。撤销命令有界等待连接关闭，超时报告未关闭的连接数而不是成功 | 立即生效且不制造不确定的副作用；run 与操作属于所有者，不因换设备丢失                          |

### D10. tsnet 的进程边界及其与系统 Tailscale 的关系（待用户决策）

| 选项 | 内容                                                                                                                                                                                                                                                                                                                                                    | 影响                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| A    | `cove-tsnet` 是 server 启动并监督的子进程（崩溃时有界退避重启）；以独立节点（默认主机名 `cove-<主机名>`，可改）加入 Tailnet，状态在 `<home>/tsnet/`（0700），不读写系统 tailscaled；接受的连接经 0700 目录中的 Unix socket 逐条转交 Node，附带 WhoIs 得到的对端节点（只用于显示与审计，不作授权）；登录用 auth key（只经 stdin 传入）或打印交互登录 URL | 网络入口崩溃或重新登录不影响 PTY；server 重启时 tsnet 节点随之重连，但身份不变          |
| B    | `cove-tsnet` 作为独立服务（自己的 launchd/systemd 单元），转发到 loopback 入口                                                                                                                                                                                                                                                                          | server 重启时 Tailnet 节点不掉线；多一个服务单元及版本协调，安装与升级更复杂            |

**推荐 A**。

### D11. CLI 作为远程 operator（待用户决策）

各选项共同的部分：全局 `--server <别名>`（或 `COVE_SERVER`）选择客户端登记的目标；`server init/install/start/service` 等本机命令
不接受 `--server`。远程模式下路径参数必须是执行主机上的绝对路径：相对路径与 `~` 在 CLI 本机以用法错误拒绝且不发送，
绝对路径原样发送、由执行主机解释（S13）；本机模式保持 M1 行为。SSH 入口每次命令启动一次 `ssh -N -L`，本地端固定绑定
`127.0.0.1`，使用用户自己的 ssh 配置、agent 与 known_hosts。

### D13. #97 过期后“永不重做”的实现方式（待用户决策）
