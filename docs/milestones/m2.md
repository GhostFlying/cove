## 交付范围

在 macOS/Linux 上：

1. **本地服务部署**（M1 D7 留下的部分）：`cove server install` 把一次构建的完整运行闭包（含固定版本的 Node、原生模块与 `cove-tsnet`）
   装到稳定的版本化目录，并注册为后台服务；服务脱离启动它的 shell、SSH 会话和任何客户端，崩溃后由服务管理器拉起。
   Linux 用 systemd user unit 加 linger，注销后与开机后都运行；macOS 用 LaunchAgent，注销时停止、登录时自动启动（D2）。
   安装新版本不会替换正在运行的 server，切换要用户显式重启；回退只限于与数据库 schema 兼容的版本（D1）。
2. **部署与重启影响可检查**：`cove server status` 报告已安装版本、正在运行的 build、服务状态、上次启动原因（手动或崩溃后拉起）
   以及是否有已安装但尚未生效的版本。`cove server restart`/`upgrade` 先列出将被中断的存活 run 及平台相关的影响，确认后才执行。
   有序重启后旧实例的 run 记为随 server 停止（stopped-with-server）；崩溃或被强杀后，下次启动把没有结束记录的 run 记为
   会话中断（interrupted，M1 D9）。都不自动重跑。
3. **设备配对与撤销**：server 签发一次性邀请，按下文的配对流程原子兑换，得到每设备独立、可撤销的长期 token；
   兑换响应丢失时重新邀请，留下的从未连接的设备可见、可撤销（D6）。撤销立即关闭该设备的活动连接并释放其控制权（D4–D8）。
4. **SSH 入口**：远程 CLI 用系统 `ssh` 把客户端 loopback 上的端口转发到执行主机的 loopback 入口，并验证 SSH host key（D3、D11）。
5. **两端内嵌 tsnet 入口**（D9、D10）：Go 模块 `native/tailscale` 构建 `cove-tsnet`，有两种模式。
   - server 端（serve）：server 启动并监督的子进程，作为独立 Tailnet 节点只监听业务与配对端口，经同机受控 IPC 把连接转交 Node。
   - 客户端（dial）：每个 OS 用户一个按需启动、空闲退出的 `cove-tsnet dial` 常驻进程（D14），是客户端节点状态的唯一所有者，作为客户端自己的 Tailnet 节点（状态在 `<home>/tsnet-client/`），连到 server 节点，
     先核实对端节点的稳定 ID 再让 CLI 发送 token；客户端节点不监听任何端口。
   - 两端都不需要系统 tailscaled；节点状态持久，普通重启不重新登录。
6. **切入口保持身份**：客户端按 serverId 记录一台 server 及其多个已验证入口（loopback、SSH、tsnet）；换入口时先核实通道对端与
   serverId，再发送 token；task、run 与终端订阅是同一份，不重复启动服务或建立新身份。
7. **CLI 作为远程 operator**：全部业务命令可用 `--server <别名>` 指向远程 server，走与本机相同的 RPC 领域方法；入口由
   `--via ssh|tsnet` 或该别名登记的固定默认入口决定，不自动换入口；远程模式下路径参数必须是执行主机上的绝对路径。
   安装、服务管理与启停仍是本机 bootstrap 边界（D11）。
8. **操作记录保存期限（#97）**：已结束（succeeded/failed/cancelled）的操作记录在结束后保存 30 天；未结束的（含 requires_attention）
   从不自动清理；重发已过期的 operationId 返回 `OPERATION_HISTORY_EXPIRED`，绝不重新执行（D13）。

M0/M1 已合入的终端链路与领域保持现状。M2 只在入口、认证与部署处接入，不重构恢复、focus 或流控。

### 明确不做

- Electron、RN/WebView 客户端与其凭据存储、移动端网络验证（M3）；Desktop 与 Mobile 的 tsnet 客户端也属于 M3（见“对 M3 的影响”）。
- Web App 与浏览器会话（二期）。
- 跨主机迁移与文件传输（M4）；发行安装器、签名、公证、自动更新与发布产物（M4）；100 终端容量验收（M4）。
- 由客户端把 server 推送部署到远程主机：M2 中每台主机在本机用自己的 CLI 安装。
- 系统 Tailscale（tailscaled）入口，以及对 `tailscale ip`、`tailscale whois` 等系统 CLI 的任何依赖（D9）。
- 应用层 E2EE、Cove 自有 TLS/CA、JWT 或客户端证书（[Server 架构 §9.4](../server-architecture.md#94-安全通道与设备授权已选择-sshtailscale) 已决定不做）。
- 裸 LAN/公网监听；自动修改防火墙；短数字配对码、二维码。
- 独立 PTY keeper；server 重启后保留 PTY。业务事件 WebSocket 订阅（随 M3 的 GUI）。
- 跨入口的自动选路与失败后自动换入口（读写命令都不换，D11）；用于选路或回退的常驻客户端代理（D14 的客户端 tsnet 进程只承载节点，不选路、不回退）；客户端 tsnet 进程作为登录项或系统服务。
- 数据库自动降级，以及回退到不兼容 schema 的旧版本（D1）。
- 配对响应丢失后的领取期限或重试路径（D6）。
- 不新增 npm package；认证与入口代码是 `apps/server` 与 `apps/cli` 的内部模块。

## 威胁模型与认证边界

M2 是 Cove 的认证边界。受信任的是通过认证的单一所有者：主机上的同一 OS 用户（能读取数据目录中的本机秘密）
与每台已配对设备。按 AGENTS.md「Trust the authenticated owner」，不防范所有者攻击自己。
已配对设备可以经终端以该用户身份在主机上执行任意命令，因此设备之间不设权限分级（D7）。

需要防范的对象：

| 对象                                                             | 能做什么                                                             | M2 的边界                                                                                                                                                                                                             |
| ---------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 同一 Tailnet 的其他节点（共享 Tailnet、他人设备、tag）           | 按 Tailnet ACL 连到 server 的 tsnet 节点；连客户端节点               | server 节点只监听业务端口与（有 `open` 邀请时的）配对端口，没有设备 token 只能完成版本握手；客户端节点不监听任何端口，tsnet 的用户态网络栈不接受未监听端口的连接；Tailnet 节点身份不替代 Cove 授权                    |
| 冒用节点名的 Tailnet 节点                                        | 在 server 节点被删除或改名后占用同一 MagicDNS 名                     | 客户端只信任配对时记录的 server 节点稳定 ID，每次连接后用自己 tsnet 节点的 WhoIs 核对对端，不符则在发送 token 前中止；从不只凭 DNS 名                                                                                 |
| 同一主机上的其他 OS 用户（多用户 devbox）                        | 连 loopback 端口，读取权限宽松的文件                                 | 秘密文件 0600、目录 0700（含两端的 tsnet 状态目录与 IPC socket 目录）；服务单元、命令行参数、环境变量与日志都不含 token、邀请 secret 或 auth key                                                                      |
| 同一主机上能连客户端 tsnet 本机 socket 的进程                    | 经常驻的 `cove-tsnet dial` 请求到 server 节点的连接，或 login/logout | socket 在 `<home>/tsnet-client/run/`（0700）中，信任只靠文件权限：能连上的只有同一 OS 用户，即所有者（D7），不另设认证；进程只代为拨号，不持有设备 token，到达 server 后仍需 token；不接受任何来自 Tailnet 的入站连接 |
| 客户端所在网络上的其他主机                                       | 连客户端为隧道开的本地端口                                           | SSH 本地转发固定绑定 `127.0.0.1` 并在命令行覆盖 `GatewayPorts`；tsnet dial 只在 0700 目录的 Unix socket 上提供给 CLI（T2、T4、S6、S8）                                                                                |
| 拿到邀请字符串的第三方（剪贴板、聊天记录、进程参数、shell 历史） | 抢先兑换                                                             | 邀请只经交互提示或 stdin 读入，不进 argv 与 shell 历史；短有效期、单次兑换、可取消、每邀请 5 次错误后作废、全局速率上限；兑换后 secret 失效                                                                           |
| 拿到 tsnet auth key 的第三方                                     | 把自己的节点加入 Tailnet                                             | auth key 只经 stdin 传入 `cove-tsnet`，不进 argv、环境变量、日志、数据库或操作记录；建议用户在 Tailscale 管理台创建一次性、带 tag 的 auth key（Cove 不检查）；即使加入 Tailnet 也仍需 Cove 设备 token                 |
| 丢失或被盗的设备                                                 | 持有长期 token 与客户端 tsnet 节点状态                               | Cove 撤销后立即失去全部连接与访问（D8）；它的 tsnet 节点仍在 Tailnet 中，需用户在 Tailscale 管理台另行移除（Cove 撤销不等于移除 Tailnet 节点）                                                                        |
| 所有者浏览器中的恶意网页                                         | 跨站请求、DNS rebinding 到 loopback                                  | 每个入口都做 M0 的 Host/Origin 校验；token 不进 URL 或 cookie                                                                                                                                                         |
| 通道中间人                                                       | 冒充 server 骗取 token                                               | SSH host key 与 WireGuard 节点密钥保证对端；客户端在发送 token 前核实通道对端（host key 或节点稳定 ID）与 serverId                                                                                                    |
| 第三方数据                                                       | `ssh` 的输出、Tailnet 节点名与 WhoIs 结果                            | 按不可信输入解析并限界，不拼进 shell 命令                                                                                                                                                                             |

不在范围：主机 OS 账户或 root 已被攻破；Tailscale 控制面或 SSH 账户被攻破（Cove 撤销不等于撤销 SSH 或 Tailnet 权限）。
tsnet 节点私钥保存在各自的状态目录中（tsnet 的文件存储，由文件权限保护）；能读到它的只有该 OS 用户与 root，属于所有者。

认证前可达的面，逐项在 S11 中验证：

- `/bootstrap` 握手：只返回 bootstrap/协议版本、build、serverId 与 relayInstanceId，供客户端在发送 token 前核对；
  不返回 task、路径、设备或终端信息。serverId 是标识，不是身份证明。
- 终端 WebSocket 在首帧认证之前的阶段（沿用 M0 的首帧期限与未认证连接预算）。
- 配对监听，只在有 `open` 邀请时存在（loopback 与 server 的 tsnet 节点上）。
- server 的 tsnet 节点：只有业务端口与配对端口，可达范围由 Tailnet ACL 决定。
- `cove-tsnet` 与 Node 之间的 IPC socket，以及客户端常驻 `cove-tsnet dial` 的本机 socket（都在 0700 目录中，只有同一 OS 用户可连）。
- 所有入口都有界：未认证连接数、请求体、首帧期限、配对尝试次数。认证失败不区分“设备不存在”与“secret 错误”，
  比较用常数时间。日志只记 deviceId、入口种类与对端节点 ID。

## 配对流程与状态

按 D6。一次配对从用户看是这样的（以笔记本配对 devbox 为例）：

1. 在 devbox 上执行 `cove auth invite create`（或在已配对设备上远程创建）。server 记录邀请，打开配对监听，
   输出一行邀请字符串，内含 serverId、入口（SSH 目标，以及 server tsnet 节点的稳定 ID 与名称）、配对端口、一次性 secret 与到期时间
   （默认 10 分钟，最长 24 小时）。
2. 在笔记本上执行 `cove remote add devbox`，在提示中粘贴这行字符串（非交互时经 stdin 传入）。邀请含一次性 secret，
   CLI 不接受命令行参数中的邀请，以免进入 argv（同机其他用户可见）与 shell 历史。经 tsnet 配对时，笔记本先用
   `cove remote tsnet login` 让自己的客户端节点登录同一 Tailnet。
3. CLI 经邀请中的入口连到配对监听，先核实通道对端（SSH host key，或 server 节点的稳定 ID），再提交 secret 与设备名。
4. server 在一个事务内完成兑换：作废 secret，新建设备，生成长期 token 并只保存其哈希，然后把 token 返回给 CLI。
   没有其他有效邀请时随即关闭配对监听。
5. CLI 把 token 与已核实的入口写入凭据文件，配对完成。之后笔记本用 `--server devbox` 直接连接，不再需要邀请。
6. 如果第 4 步的响应在路上丢了：这个邀请已经兑换，不能重试，也没有额外的恢复路径。用户在 devbox 上重新创建邀请再配对一次。
   那次兑换留下的设备从未连接过，在 `cove auth device list` 中标为“从未连接”（never-connected），可以直接撤销。

| 邀请状态                           | 进入条件                                              | 离开                                                                                         |
| ---------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `open`                             | 签发（本机 CLI 或已配对设备）                         | 兑换 → `redeemed`；取消 → `cancelled`；到期 → `expired`；错误 secret 达到 5 次 → `cancelled` |
| `redeemed`、`cancelled`、`expired` | 见上；`redeemed` 的兑换在一个事务内完成，同时新建设备 | 终态；对终态邀请的任何兑换请求都被拒绝                                                       |

- **配对监听**：至少有一个 `open` 邀请时开放；最后一个 `open` 邀请兑换、取消或到期后关闭，不影响业务端口、已连接设备与 PTY。
- **拒绝不透露原因**：对已兑换、已取消、已过期或不存在的邀请，以及错误的 secret，都返回同一错误（`INVITATION_UNAVAILABLE`）。
- **从未连接的设备**：设备记录有最后使用时间；从未用 token 成功认证过的设备在列表中标为 never-connected，与其他设备一样可撤销；
  Cove 不自动撤销它。
- **重启**：邀请与设备状态存在 SQLite，期限按墙钟计算；server 重启后若仍有 `open` 邀请，配对监听重新开放（S12）。

## 秘密与操作记录的分界

现有写操作会保存规范化参数、指纹与结果，CLI 也会保存待定请求，秘密不能沿用这些机制。T0 在方法表中为每个方法声明秘密字段，
由分派层与 CLI 统一执行：

1. **含秘密的方法**：`auth.invite.create`（输出邀请 secret）、`auth.device.rotate`（输出新 token）、`server.tsnet.login`（输入 auth key）。
   配对兑换走配对监听，不是 RPC 操作，不建操作记录。客户端节点的 `cove remote tsnet login` 只在客户端本机执行，不经 server，也不建操作记录。
2. **输入秘密**不进入操作指纹、规范化参数与操作记录；auth key 经 stdin 交给 `cove-tsnet` 后即丢弃。
3. **输出秘密**只出现在这一次实时响应中；操作记录的 result 只保存非秘密部分（inviteId、到期时间、deviceId）。
   `operation get` 与同一 operationId 的重发返回该记录，不含秘密，并注明秘密只交付一次。
4. **丢失的一次性秘密不能取回**，恢复是新的显式操作：邀请——`auth invite cancel` 后重新创建；token 轮换——两阶段，
   新 token 首次认证成功前旧 token 仍有效，响应丢失时用旧 token 再次轮换，替换尚未使用过的新 token；tsnet 登录——用
   `server tsnet status`（或 `remote tsnet status`）查看结果，必要时用新的 auth key 重新登录。
5. **CLI 输入**：邀请字符串与 auth key 只经交互提示或 stdin 读入，CLI 不提供接收它们的命令行参数；错误输出与诊断不回显它们。
   **CLI 待定记录**不保存秘密字段；有秘密输入的请求不能 `operation resend`，CLI 在本机拒绝并提示重新执行原命令。
6. 设备 token 与邀请 secret 在 server 端只以哈希存储；日志、错误与诊断不含任何秘密。有意保存在磁盘上的秘密只有：
   客户端凭据文件中的设备 token（0600），以及两端 tsnet 状态目录中的节点私钥（目录 0700）。

## 验收场景

每个场景是启动编译产物（`cove-server`、`cove` CLI，以及 `cove-tsnet`）的自动化测试，用临时数据目录与临时客户端目录，
不触碰真实 `~/.cove`、用户的服务单元、ssh 配置或 Tailnet。同一台机器上用两个客户端目录模拟两台设备。
需要丢弃响应时，由测试夹具中的转发代理在响应到达客户端前断开连接，不在 server 中加测试钩子。
tsnet 场景在 CI 中使用 Tailscale 的测试控制面（若 T5a 证实可行）把两个 `cove-tsnet` 节点连起来；否则只在真实 Tailnet 上验证。

## 任务拆分

每个任务一个 PR，由独立 subagent 在各自 worktree 实现；每个 PR 带上自己负责的场景测试，测试放在 `apps/cli/tests/m2/`，
按 M1 的 `.suite.json` 方式登记。每个改变 tend 可见接口（CLI 命令、参数、退出码、JSON 输出）的 PR 同时更新
[Shepherd/tend 集成说明](../integrations/shepherd-tend.md)。共享入口各有唯一写入者：

- **协议 schema、方法表、错误码、bootstrap 与客户端**：T0 唯一写入。T0 定义全部 M2 方法、错误码与每个方法的秘密字段，
  在 server 分派中为 `auth`、入口与服务状态建只返回 `CAPABILITY_UNAVAILABLE` 的初始模块，把认证结果作为主体（本机所有者或 deviceId）
  传入分派。之后的任务只替换自己的模块。
- **测试登记**：T0 在 `scripts/ci-test-gate.mjs` 的 `fileRegisteredDirectories` 中登记 `apps/cli/tests/m2`（第一个测试合入前目录可以为空），
  使 T1 的第一个测试 PR 能独立通过 CI；之后各任务只新增自己的测试与 `.suite.json`，不改门禁脚本。
- **存储操作注册**：T0 新建空的 `apps/server/src/store/sql/auth.ts` 并在 `sql/registry.ts` 注册；T1 只填充 `sql/auth.ts`，
  并是第 2 轮中 `sql/writes.ts` 的唯一写入者；T6 只改 `sql/receipts.ts` 与 `store/operations.ts`，不改注册表与 `writes.ts`。
- **server 入口注册**：T3 建立监听集合（loopback 业务端口、配对端口、tsnet），tsnet 先注册为返回 `ENTRY_UNAVAILABLE` 的占位，
  T5b 只替换自己的模块，不再改集合本身。

  的占位 `remote/tsnet.ts`，T4 只替换它。
- **CLI 路由**：`cove server ...` 的子命令都由 `commands/server.ts`（T3）分派，T3 为 `server tsnet` 建只返回 `CAPABILITY_UNAVAILABLE`

  `commands/remote.ts`（T1）分派，T1 为 `remote tsnet` 建委托占位 `commands/_remote_tsnet.ts`，T4 只替换它。

## 已决策

用户于 2026-10-21 对 D1–D14 作出以下决定。已确认的既有决策（固定 serverId、每设备可撤销凭据、一次性邀请、
SSH/Tailscale 提供通道安全而 Cove 负责设备授权、不做 E2EE/自有 TLS/JWT、tsnet 用 Go、配对监听只在有效邀请期间开放、
无 keeper、CLI 为完整操作入口、协议首个正式版本前不提升版本）不变。Orca 对照见文末。

### D1. 安装目录布局（选 A）

- `<home>/install/<build>/` 存放一次构建的完整运行闭包（server、CLI、worker、生产依赖与原生模块、固定版本的 Node、`cove-tsnet`），
  安装后不再修改；`<home>/install/current` 符号链接原子切换；服务单元与 `<home>/bin/cove` 只引用 `current`；数据仍在 `<home>/server`；
  旧版本保留，`install --prune` 显式清理不在运行的版本。安装来源是本机的仓库构建，发行产物属于 M4。
- 回退：M1 D5 的构建拒绝打开 schema 更高的数据库，而新版本启动时会前进迁移，所以切回旧目录只对与当前数据库 schema 兼容的版本有效。
  `install --activate <build>` 在切换前检查目标版本支持的 schema，不兼容时拒绝并说明原因，数据库不变。Cove 不自动降级数据库，
  也不自动恢复迁移前的备份；确需回到不兼容的旧版本时，用户先停止服务，手动用迁移前 `VACUUM INTO` 留下的备份替换数据库
  （备份之后的记录会丢失），再激活旧版本。开发说明给出这一步骤，CLI 不代为执行。
- 未选：B（平台惯例位置，与数据目录分处两地）；C（服务单元指向构建 checkout，违背[Server 架构 §5](../server-architecture.md#5-持久服务与-pty-的存活边界)）。

### D2. 服务管理器与各平台的运行保证（macOS LaunchAgent、Linux systemd user + linger，停止清理用默认值）

- 两个平台都脱离启动它的 shell、SSH 会话与任何客户端；崩溃后有限次数拉起，正常退出不拉起；`server status` 报告启动原因。
- **Linux**：systemd user unit 加 linger，开机即运行，注销后继续运行。未开启 linger 时 CLI 报告并给出 `loginctl enable-linger` 命令，
  不自行 sudo；没有 systemd user 的主机（容器等）继续用 M1 的前台 `cove server start`。
- **macOS**：用户 LaunchAgent（`~/Library/LaunchAgents`，gui 域），不需要提权。用户接受：登录后自动启动；**注销时停止**，server 与全部 PTY
  结束，run 记为随 server 停止（stopped-with-server），不自动重跑；开机后用户登录前不运行。它运行在用户的登录会话中，ssh-agent、
  钥匙串与 TCC 授权和用户平时的终端一致。
- **停止时的进程清理**：用 systemd 默认的 `KillMode=control-group`。停止或重启服务会结束 cgroup 内全部进程，**包括用户在 Cove 终端里用
  `nohup`、tmux 等脱离的进程**；这与前台运行 `cove server start` 时不同。这一后果写进 `server.impact` 的输出、重启确认提示与开发说明（S2）。
  macOS 的 LaunchAgent 结束 server 时，终端里脱离的进程是否保留由 launchd 与进程会话决定，在 S1 的实机验证中记录实际行为并写入文档。
- 未选：macOS 系统 LaunchDaemon（注销不受影响，但安装、切换与卸载要 sudo，且不在登录会话中：没有 ssh-agent，钥匙串与 TCC 访问不同）；
  两者都提供；Cove 自行后台化（没有崩溃拉起与可依赖的注销行为）；`KillMode=process`（保留脱离的进程，但崩溃或强杀后可能留下无人管理的孤儿进程）。

### D3. 本机入口与稳定端口（选 A）

固定的 loopback TCP 业务端口与配对端口：写入 server 配置，`install` 时选定空闲端口，经 CLI 修改（需重启生效）；
SSH 与 tsnet 都转发到同一套处理。认证边界是 token；同机其他 OS 用户能连上端口，但没有 token 只能握手。
未选：B（主入口改为 Unix socket）；C（两者都提供）。

### D4. 设备凭据格式与 server 端存储（选 A）

不透明 bearer token `cove_d1_<deviceId>.<256 位随机 secret>`；server 只存 secret 的 SHA-256（高熵，无需慢哈希），按 deviceId 查找后
常数时间比较；设备记录（名称、创建时间、来源邀请、最后使用时间与入口、撤销时间）存 SQLite；长期有效，`auth device rotate` 两阶段轮换
（见“秘密与操作记录的分界”）。本机 CLI 不用设备 token，仍用数据目录中的每次启动秘密（D7）。
未选：B（短期 access token 加 refresh token）；C（JWT 等签名令牌，已决定首期不用）。

### D5. 客户端凭据存储（选 A）

CLI 把别名、serverId、已验证入口（SSH 目标与 host key 由 ssh 自己管理；tsnet 记录 server 节点稳定 ID）与 token 存在
`<home>/client/servers/<serverId>.json`（文件 0600、目录 0700，原子写入）；客户端 tsnet 节点状态在 `<home>/tsnet-client/`（0700）。
M3 的 Desktop 经宿主接口使用系统钥匙串。未选：B（系统钥匙串，无图形会话的 Linux 主机不可用）；C（钥匙串优先，回退到文件）。

### D6. 配对监听、邀请与响应丢失（选 A，响应丢失时重新邀请）

- 配对监听用独立端口（D3），只在有有效邀请时、在 loopback 与 server 的 tsnet 节点上开放。邀请字符串 `cove-invite:v1:<base64url>` 含 serverId、
  入口（SSH 目标、server tsnet 节点的稳定 ID 与名称）、配对端口、inviteId、256 位 secret 与到期时间；默认 10 分钟，最长 24 小时。
  每个邀请错误 secret 达到 5 次后作废，另有全局速率上限。
- 兑换是一个原子事务；最后一个有效邀请兑换后关闭配对监听，与已确认约束（[Server 架构 §9.3](../server-architecture.md#93-单用户设备配对)）一致。
- 用户的理由：兑换响应丢失很少见，对一次性的配对也不重要，因此不设领取期限、重试或额外的恢复路径。用户重新创建邀请再配对；
  丢失响应留下的设备在设备列表中标为 never-connected，可以撤销。为最简单起见，连监听仍开放时的重试也不保留：兑换请求不带申请密钥，
  客户端也不保存配对待定文件。流程见上文“配对流程与状态”。
- 未选：配对走业务端口上的路径（改变已确认约束）；兑换后保持监听开放的领取期限，或业务端口上的领取端点。

### D7. 主体与权限（选 A）

两类主体：本机所有者（能读数据目录中本机秘密的同一 OS 用户，不可撤销，是 bootstrap 边界）与已配对设备。所有设备权限相同，
包括签发邀请、撤销其他设备与修改配置；服务的安装、启停与升级只能在本机 CLI 执行。操作记录键中的 principalId 仍是所有者，
发起设备另记 deviceId（[协议 §11.3](../relay-protocol.md#113-去重并发与保存期限)）。设备本就能经终端执行任意命令，分级挡不住已认证设备。
未选：B（admin/operator 分级）；C（设备管理只在本机，违背已确认的“已配对 desktop 可申请邀请”）。

### D8. 撤销对活动连接的语义（选 A）

一个事务内标记设备撤销并取消它创建且未兑换的邀请；提交后拒绝它的新请求（`DEVICE_REVOKED`），以撤销原因关闭它的全部 WebSocket，
释放它持有的终端控制权（epoch 前进，不 resize），丢弃尚未发出的响应；它已受理的操作照常执行完毕，记录可由其他设备查询；
它启动的 run 继续运行。撤销命令有界等待连接关闭，超时报告未关闭的连接数而不是成功。撤销不移除该设备的 tsnet 节点。
未选：B（同时取消进行中的操作，结果不确定）；C（只拒绝新请求，违背已确认要求）。

### D9. 网络入口：不使用系统 Tailscale（范围变更）

用户决定 Cove 不使用系统 Tailscale，两端都只用自己内嵌的 tsnet，理由是有些设备无法安装 tailscaled。因此：

- 去掉系统 Tailscale 入口：原 T4（系统 Tailscale）删除，`--via` 只有 `ssh|tsnet`，不调用 `tailscale ip`、`tailscale whois` 或任何系统 CLI。
- server 端按 D10 运行 `cove-tsnet serve`，作为独立节点加入 Tailnet。
- 客户端（新增）：CLI 经 `cove-tsnet dial` 连到 server 节点，有自己的客户端节点状态（`<home>/tsnet-client/`，0700）与登录
  （auth key 经 stdin，或交互登录 URL），并用自己节点的 WhoIs 核对对端稳定 ID 与配对时记录的一致；从不只凭 DNS 名信任对端。
  两端都不需要系统 tailscaled。
- Desktop 与 Mobile 的 tsnet 客户端属于 M3（见“对 M3 的影响”），M2 不预建。
- [工程计划 §4](../engineering-plan.md#4-建议的里程碑与退出条件) 的 M2 一行改为 SSH 与两端内嵌 tsnet；server-architecture 中系统 Tailscale 的内容由 T7 改写。

### D10. tsnet 的进程边界（选 A）

`cove-tsnet serve` 是 server 启动并监督的子进程（崩溃时有界退避重启）；以独立节点（默认主机名 `cove-<主机名>`，可改）加入 Tailnet，
状态在 `<home>/tsnet/`（0700）；只监听业务端口与（有 `open` 邀请时的）配对端口；接受的连接经 0700 目录中的 Unix socket 逐条转交 Node，
附带 WhoIs 得到的对端节点（只用于显示与审计，不作授权）；登录用 auth key（只经 stdin 传入）或打印交互登录 URL。
网络入口崩溃或重新登录不影响 PTY；server 重启时节点随之重连，身份不变。客户端的 dial 模式见 D9，由同一可执行文件提供。
未选：B（`cove-tsnet` 作为独立服务）；C（c-shared 库载入 Node，崩溃会带走 server 与 PTY）。

### D11. CLI 作为远程 operator（选 A）

全局 `--server <别名>`（或 `COVE_SERVER`）选择客户端登记的目标；入口由 `--via ssh|tsnet` 指定，未指定时用该别名登记的固定默认入口
（`remote add --via ssh` 时为 ssh，`--via tsnet` 时为 tsnet，同一主机不带 `--via` 时为 loopback；
可用 `remote entry default` 修改；2026-10-22 用户确认配对所用入口为默认入口）；连接失败时读写命令都直接失败并列出可用的 `--via`，不自动换入口。
SSH 入口每次命令启动一次 `ssh -N -L`，本地端固定绑定 `127.0.0.1`，使用用户自己的 ssh 配置、agent 与 known_hosts；tsnet 入口经按需启动的常驻 `cove-tsnet dial` 连接（D14）。远程模式下路径参数必须是执行主机上的绝对路径：相对路径与 `~` 在 CLI 本机以用法错误拒绝且不发送，
绝对路径原样发送、由执行主机解释（S13）；本机模式保持 M1 行为。`server init/install/start/service` 等本机命令不接受 `--server`。
`ssh host cove ...` 始终可用（能登录主机的 SSH 用户本就是本机所有者）；tend-runner 仍调用本机 CLI，不受影响。
未选：B（有界的只读入口回退）；C（不做远程模式）；为选路或回退而设的常驻本地代理进程。D11 原先的“不设常驻进程”由 D14 修改：
客户端 tsnet 节点由一个常驻进程承载，但它不选路、不回退，固定入口与失败不换入口不变；SSH 入口仍是每次命令一个 `ssh` 进程。

### D12. 新方法的协议版本（选 A）

按首个正式版本前的规则不提升 protocolVersion、不加能力协商，不同构建相遇不受支持（[协议 §10](../relay-protocol.md#10-发布门槛与验证)）；
server 报告真实 buildVersion，CLI 在 build 不同时只在 stderr 警告。未选：B（build 不同即拒绝）；C（提升 protocolVersion）。

### D13. #97 过期后“永不重做”的实现方式（选 A）

用户已决定策略（30 天、未结束的不清理、过期重发返回明确错误且不执行）。30 天后删除完整记录，保留精简 tombstone
（operationId、指纹摘要、方法、终态、结束时间，约百字节）且不再删除；对 tombstone 的重发返回 `OPERATION_HISTORY_EXPIRED`。
tombstone 增长很慢（每天千次写操作约每年 36 MB）。未选：B（带时间的 operationId，依赖客户端时钟且要改 tend 的 ID 格式）；
C（tombstone 也定期删除，期限后可能重新执行）。

### D14. 客户端 tsnet 节点的并发所有权（选 B：按需启动的常驻客户端进程）

问题：多条远程命令会重叠（保持终端接入时另开一条命令，或接入期间 `remote tsnet logout`），而 tsnet 的文件状态存储只有进程内互斥
（读取后缓存整份状态，写入时整份替换文件），两个进程用同一个节点密钥同时上线也会互相争用。用户决定：

- **单实例所有权**：每个 OS 用户一个 `cove-tsnet dial` 进程，是 `<home>/tsnet-client/` 的唯一所有者。它对 `<home>/tsnet-client/run/lock`
  持有内核排他文件锁（进程退出即由内核释放），持锁后才打开节点状态，并在同一 0700 目录中监听 `run/dial.sock`。
- **启动与空闲退出**：经 tsnet 的命令先连 socket；连不上时启动一个脱离的 dial 进程，并有界等待（默认 10 秒）socket 就绪，
  超时以 `ENTRY_UNAVAILABLE` 失败并给出进程的诊断输出。没有活动流且没有控制请求达到空闲期限（默认 10 分钟，可在客户端配置中修改）后退出，
  先删除 socket 再释放锁。它不是登录项或系统服务，不随登录启动。
- **崩溃恢复与启动竞争**：判定以锁为准，不以 socket 文件是否存在为准。新进程取得锁后删除残留的 socket 文件再监听；取不到锁的新进程
  直接退出。CLI 不把一次竞争失败当作“已有实例即将就绪”的证明（持锁者可能正在空闲退出——socket 已删、锁未释放——或在就绪前崩溃），
  而是在同一个总启动期限（默认 10 秒）内循环：连接 socket，失败则再次尝试启动并短暂退避，直到连上或期限用尽后以 `ENTRY_UNAVAILABLE` 失败。
  这种重试只发生在提交任何业务请求之前；流一旦建立、请求已发出，连接中断就按下一条处理，不重试。已建立的流随 dial 进程崩溃时按连接中断处理：终端接入从基线加增量恢复，
  不确定是否送达的写操作按 M1 的操作记录规则查询，不自动重发终端输入。
- **并发命令**：每条命令在 socket 上请求一条到指定 server 节点稳定 ID 的流，dial 进程在一个节点上复用多条流，长时间接入不阻塞其他命令；
  每条流建立前都用 WhoIs 核对对端，与配对记录不符则拒绝该流。
- **login/logout**：`cove remote tsnet login/status/logout/stop` 都作为控制请求发给 dial 进程（必要时先启动它），在进程内串行执行；
  auth key 经 CLI 的 stdin 读入后经 socket 传给 dial 进程，不进 argv、环境变量与日志。logout 与 stop 有活动流时列出它们，
  不带 `--yes` 以非 0 退出，带 `--yes` 时先关闭活动流；logout 随后登出节点并删除节点状态，stop 只结束进程。
- **本机 socket 的信任**：只靠文件权限（目录 0700、socket 0600），能连上的只有同一 OS 用户，即所有者（D7），不另设认证；
  dial 进程不持有设备 token，token 仍由 CLI 在流建立后发给 server。
- **升级与版本不符**：连接 socket 时双方先交换本机 socket 协议版本与 build。build 相同则继续；不同时，若 dial 进程没有活动流，
  CLI 请它退出并启动当前安装的版本；若有活动流，绝不悄悄替换：本机协议版本兼容时沿用旧进程并在 stderr 警告，不兼容时以明确错误失败，
  列出活动流并提示等待其结束或 `remote tsnet stop --yes`。与 D1 一致，安装新版本不会结束正在运行的旧 dial 进程。
- **归属**：T5a 在 Go 中实现 dial 进程本身（锁、socket、空闲退出、残留接管、流复用、控制请求与本机协议版本）；
  T4 实现 CLI 一侧（按需启动与有界等待、版本检查与替换规则、`remote tsnet` 命令与入口接线）。

未选：A（每条命令一个 dial 进程加排他锁，长时间接入会挡住其他经 tsnet 的命令，且每条命令都有节点启动延迟）；
C（每条命令一个临时节点，需要长期保存可复用的 auth key 或每次登录，节点 ID 每次不同）。
