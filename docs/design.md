# Cove 设计草案

状态：讨论中。本文区分用户已确认的需求与建议方案，不代表功能已实现。

## 1. 已确认的产品边界

- 保留 Orca 按 task 组织工作的简单体验。
- 列表只展示 Cove 管理的 task/workspace 及其显式挂载，不自动枚举展示仓库的所有 worktree。
- 首期原生平台：macOS desktop、macOS/Linux server、iOS/Android mobile。macOS desktop 使用 Electron。
- Web App 已纳入二期，当前只考虑经 Tailscale 访问；一期保留共享 UI/client 边界，不以 Web 交付为前置。
  Desktop renderer 与 Web App 共用 Web UI 和客户端协议层，Electron 提供宿主能力。
- 初版 mobile 使用 React Native + WebView 承载终端，首个终端后端已选 xterm.js。
  Lynx + WebGL / WebGPU 留作后续评估，不作为首期交付前置条件。
- 调查等轻量任务可以直接使用已有主仓库，不必创建独立 worktree。
- 同一 task 在进行中可以更换工作位置，包括转入独立 worktree，并考虑跨设备迁移。
- 一个 task 可以涉及多个仓库，各仓库可以使用自己的 worktree。
- 创建 task 时默认沿用当前仓库，直接提供“使用当前目录”和“创建独立 worktree”。
  创建菜单内可以一次添加多个 repo/worktree，也可以在任务创建后继续添加。
- 仓库须提前注册；跨主机迁移要求目标主机已有对应仓库的注册。
- 注册 repo 可位于任意路径，托管 workspace 使用每个 server 统一且可配置的根目录。
- 每个 workspace 都有独立入口目录，单仓也增加这一层；agent/终端默认 cwd 是 workspace root。
- TUI、持久会话和 remote 是核心；初版只支持 TUI，有限 chat UI 放到二期，参考 Orca 的交互形态。
- TUI/terminal 实现必须可插拔，允许后续替换引擎或渲染后端；首个实现不是永久技术绑定。
  后续可评估 Lynx + WebGL / WebGPU，具体运行时能力在接入时验证。
- Relay 是可独立运行的持久 host server，支持多客户端直接连接和状态同步，不经过 macOS desktop 中转。
- Server 同时设计内置 Tailscale 与 host 网络两种接入方式，连接同一套状态和终端。
- 客户端全部断开不触发 server 退出或 PTY 清理，终端继续运行，后续可以重新接入。
- 初版不提供独立 PTY keeper；server 重启明确提示会话影响，保留 tab 记录供事后手动恢复。
- 终端持久化选择 A：保留 tab 配置与运行记录，不落盘终端画面、恢复基线或 scrollback；最后的 agent 业务状态后续通过 hook 实现。周期快照仍在内存中维护。
- 已选部署方案 B：Electron 与本地 server 独立，server 内含 runtime 与终端子进程池；Desktop 退出或更新不隐式重启 server，一期不保证 runtime 重启后接管存活 PTY。
- 已确认终端查询由执行主机的权威模型唯一回复，不随客户端连接、focus 或可见性切换回复方；客户端自动回复及历史回放不得写回 PTY。
- Tab 需区分正在执行、近期有命令和长期闲置；活动状态与会话存活、客户端焦点分别表达。
  状态不限制为三类，可细分；CLI 和 GUI 共享结构化状态语义。
- 同机切换工作位置只影响新会话，已有会话保留实际位置；跨主机迁移前结束相关活跃终端。
- 终端尺寸跟随当前操作者；客户端终端获得有效 focus 时，通过显式协议自动取得控制权并调整尺寸，
  不弹恢复尺寸或接管确认框。后台订阅不触发 focus，观看者沿用服务端网格。
- Relay 协议版本独立于客户端和 relay 的发布版本。同一协议版本必须兼容；
  协议版本不同时明确提示 recovery/reset，不自动替换 relay 或遗弃原会话。
- 一期不做 managed agent，也不做 agent 原生 session 的无损迁移或远端数据库改写。
  跨设备时可考虑复制 rollout；是否实现及具体格式支持仍待定。
- Mobile 提供相同核心工作流。
- 初版 mobile 不内嵌 Tailscale，使用手机系统的 Tailnet 路径；移动端 SSH 后续评估。
- 单用户、多设备，设备凭据可撤销；host 网络与 Tailscale 共用相同授权规则。
- 远程连接已选 SSH/Tailscale 提供通道加密与对端验证，Cove 保留一次性邀请和独立设备 token。
  首期不提供裸 LAN/公网明文入口，不实现应用层 E2EE 或自建证书体系；本机使用 Unix socket/loopback。
  Web 入口建议使用 Tailscale 自动管理证书的 HTTPS/WSS，详见 Server 架构 §9.5。
- Cove 原生 CLI 是 first-class operator，按领域划分子命令，覆盖能力全集；后续新增能力必须提供完整 CLI 操作与配置。
  GUI 是同一能力的交互映射；agent 可使用 CLI，不依赖用户维护配置文件。
- 初期不提供通用设置 UI，允许 CLI 与客户端通过同一授权 API 远程修改 server 设置。
  授权、配对等必要交互可提供 GUI，同时保留完整 CLI 入口。
- 定时任务纳入后续范围，明确不首发；具体触发与执行语义在对应阶段设计。
- Relay 承载任务迁移所需的数据传输；具体传输范围和首发迁移能力另行收敛。
- Shepherd 不进入一期，未来作为独立看板系统接入。

## 2. 核心模型与建议约束

**一个 Task 对应一个 Workspace；Workspace 的身份稳定，内部挂载和执行位置可以变化。**

```text
Task
└── Workspace
    ├── 当前执行位置：Host + revision
    ├── Mount A：已有 checkout / 托管 worktree / 普通目录
    ├── Mount B：已有 checkout / 托管 worktree / 普通目录
    └── Tabs：每个 tab 保留记录，运行实例绑定启动时的 host、路径和 workspace revision
```

用户仍然只需要打开一个 task。单仓任务是只有一个仓库挂载的 workspace，不另建一套模型。
新任务也可以暂时没有挂载；执行需要目录的操作前再选定工作位置。

### 2.1 概念与身份

| 概念 | 含义 | 身份是否随迁移变化 |
| --- | --- | --- |
| Task | 用户要完成的工作、标题、目标和归档状态 | 不变 |
| Workspace | 此 task 的工作环境，建议每个 task 恰好一个 | 不变 |
| Mount | workspace 内一个有稳定名称的仓库或目录位置 | 可保留；底层绑定可以替换 |
| Repository | 用户登记的逻辑仓库；可以有多个主机上的 clone | 不变，不直接以路径或 remote URL 作为唯一 ID |
| Host repo registration | 某主机上已登记的仓库位置，关联逻辑 repo 与当地 clone | 各主机独立；迁移时选择目标注册 |
| Binding | mount 当前指向的 host、clone、目录、分支及所有权 | 可以变化，并留下历史 |
| Terminal tab | task 下持久的逻辑终端记录；可没有运行实例，也可在原实例结束后明确重开 | 保留 tab 身份；重开创建新的运行实例 |
| Terminal session | Cove 管理的 PTY 与终端连接；agent 原生会话 ID 仅是可选关联 | 原 session 不随元数据切换而移动 |

一个 mount 的三种来源：

- `checkout`：使用已有主仓库或已有工作目录；Cove 不拥有该目录。
- `worktree`：为此任务创建并管理的独立 Git worktree。
- `directory`：普通目录，不要求存在 Git。

来源和权限分开表达。使用主仓库不意味着技术上只读，也不自动授权修改。
调查任务可提示 agent 以只读方式工作；在没有实际沙箱限制时，界面不得声称已经强制只读。

### 2.2 一期建议保持的约束

- 一个 workspace 当前只在一个执行主机上活动；多个 repo 在该主机上共同使用。
- 一台设备可以作为客户端查看另一台设备上的 workspace。
- 切换客户端与迁移执行主机是两种操作。手机接入远端 session 不发生任务迁移。
- 同一仓库可以在多个 task 中出现。共享已有 checkout 时要展示共享关系，不能让用户误以为已经隔离。
- workspace 的工作目标、执行主机和 session 都不从当前页面或 tab 是否存在来推断。

同时跨多台主机联合执行的 workspace 暂不纳入一期建议范围；未来可增加执行位置，
但不需要现在为此引入分布式文件系统或跨主机目录映射。

### 2.3 仓库提前注册

Task 创建与 repo 注册是两个不同操作。用户先在某个 host 上注册仓库，再从注册列表选择
已有 checkout 或以该仓库为基础创建独立 worktree。

建议注册信息至少包括稳定 ID、host ID、实际 clone 路径和显示名称。
跨主机的对应关系使用显式映射；remote URL 可以辅助推荐，不能仅凭 URL 或目录名自动认定身份。

- “当前仓库”作为默认值的前提，是当前 host 上已经注册；未注册时提供注册入口。
- 本机注册不会自动变成远端注册，迁移也不隐式 clone 或注册缺失仓库。
- 多仓迁移逐一选择目标 host 上对应的注册；全部满足后才开始准备目标工作位置。
- 注册存在不等于目录仍可用；执行前需要在所属 host 验证实际仓库。
- 已有主仓库是外部资源；从它创建的 task worktree 单独记录 Cove 的管理关系。

普通目录不是 Git repo，不伪装成 repo 注册；其登记方式另行确定，跨主机时需明确选择目标目录。

### 2.4 创建 task

建议创建菜单提供：

1. task 标题及可选初始说明。
2. 执行 host，默认沿用当前上下文。
3. 第一行仓库，默认当前已注册仓库；直接选择“使用当前目录”或“创建独立 worktree”。
4. “添加仓库”入口，在同一菜单增加第二行及更多行，每行独立选择已注册 repo 和工作位置。
5. 一次创建 task 及其 workspace，不要求先创建单仓 task 再回头添加其他仓库。

单仓用户只需处理第一行，多仓用户可以一次完成配置。创建后仍允许增加、更换或移除挂载。
已有 worktree 可作为已有工作位置选择；不会因被选中就自动成为 Cove 可删除的资源。

多仓准备逐仓报告结果，部分失败时保留已完成步骤供重试，不自动启动指向缺失目录的终端。
task 进入可执行状态前展示最终挂载清单，不能把部分成功表现为全部完成。

### 2.5 只展示 Cove 管理的工作

Task/workspace 列表来自 Cove 的资源记录，不从 `git worktree list` 或目录扫描生成。
注册 repo 只让该仓库成为创建工作位置的来源，不自动导入它现有的 worktree。
其他工具创建的 worktree 不因位于 workspaceRoot 下、分支名相似或属于同一 clone 而自动出现。

用户明确创建的调查 task 即使引用已有 checkout，也属于 Cove 管理的 task，正常展示。
这里区分管理关系与文件所有权：外部目录可以被显式挂载，但不会因此成为 Cove 可自动删除的资源。
已有 worktree 的显式路径引用仍可使用，不提供自动导入全部外部 worktree 的列表流程。

Git 枚举可用于目标路径冲突检查、操作验证和诊断，但结果不提升为列表项目。
已登记的托管 worktree 被外部删除时，保留对应 task 并标记绑定缺失，不丢任务也不静默重建。
Server 的列表 API 和各客户端统一遵循此规则，不能只在 UI 隐藏已经自动导入的资源。

## 3. 工作流：从调查到独立 worktree

示例：task 起初调查一个仓库，后来发现需要改代码。

1. 创建 task，workspace 的 repo 挂载指向已有 checkout，不创建分支和 worktree。
2. 用户选择“转到独立 worktree”。Cove 展示来源、基准提交、新分支、目标位置和已有改动。
3. 准备目标 worktree，验证 Git 状态和需要的环境。
4. 验证通过后切换挂载绑定，并增加 workspace revision。
5. 后续 session 使用新目录；旧 session 保留其真实的原始绑定，不伪装成已经迁移。

默认保留 task、workspace、mount 的 ID、历史记录和附件关联。
如用户想拆出一个独立任务，应是另一个明确操作，而非隔离 worktree 的副作用。

### 3.1 已有改动的处理

- 来源干净：可直接从所选提交准备目标。
- 来源存在改动：先区分“从提交开始，不带改动”和“携带选定改动”。
- 来源是共享 checkout 时，不能默认所有未提交内容都属于当前 task。
- 不通过自动 stash、reset、切换来源分支或删除来源文件来实现迁移。
- 携带改动必须考虑已暂存、未暂存、未跟踪、二进制文件以及文件权限；
  被忽略文件和本地配置需要明确的处理策略，不能隐式全量复制或悄悄丢弃。
- 未提供保留暂存状态等能力时必须展示限制，不能只比较最终工作目录就宣称完整迁移。

携带改动前需要用户结束或停止相关写入，并检查源内容是否在快照过程中变化。
Cove 无法仅凭自身锁阻止外部编辑器修改共享 checkout，因此变化检测失败时应重新准备，
不能宣称取得了原子文件系统快照。

### 3.2 终端模型与 agent 边界

Cove 负责终端的创建、输入输出、尺寸、接入、重连和用户明确要求的停止操作。
Agent 是在终端中运行的普通 CLI；一期提供启动命令与状态识别，二期再提供有限 chat UI，
但不接管 agent 的执行循环、原生会话数据库或内部恢复过程。

本文中的 session 默认指终端 session。Agent 原生会话与 rollout 属于外部工具的数据，
关联到它们不意味着 Cove 已经托管或能完整迁移它们。

切换 mount 的路径不会改变已运行 shell 或 agent 的 cwd。
即使发送 `cd`，也不能假定 agent 内部缓存、工具上下文和恢复路径已经更新。

一期的处理方式：

- 在新位置启动新 session，原 session 留在历史中。
- 用户可以使用 agent 自己支持的命令继续工作；Cove 不保证原生会话被自动恢复。
- 不引入 agent 自动暂停、checkpoint、热迁移或自动生成交接摘要的必需流程。

旧 session 的停止必须是用户可见的操作。若旧 session 仍可写来源，界面必须持续展示其原位置。
无法确认来源是否停止时，不默认在目标自动启动另一个写入者。
初版跨主机迁移要求先结束相关活跃终端，再执行内容传输与交接；不会自动结束用户进程。
Tab 的生命周期、活动分类和重开记录见 [终端状态设计](terminal-architecture.md#12-tab-状态与-server-重启后的重开)。

## 4. 多仓 workspace

示例：同一 task 同时修改服务端和客户端。

```text
Task: 支持新的消息类型
Workspace:
  server -> server repo 的 task worktree
  client -> client repo 的 task worktree
  docs   -> 文档仓库的已有 checkout
```

各挂载分别保留自己的 repo、基准提交、分支和 Git 状态。
分支名称可以默认相似，但不能要求多个仓库有同一分支或同一提交关系。
worktree 是独立仓库的工作目录，不因为加入 workspace 就成为 Git submodule。

### 4.1 呈现和操作

- task 页面统一展示挂载列表，每个仓库独立显示 branch、diff、运行位置和异常。
- 单仓和多仓均默认从 workspace root 启动，向 agent 明确列出各仓库入口与真实路径。
- 新增、移除、更换一个挂载，不改变其他挂载的归属。
- Git 操作必须明确目标仓库；可以提供批量入口，但逐仓展示结果。
- 多仓提交、推送不宣称原子成功；部分完成必须可见并可继续。

### 4.2 统一 workspace 根目录

已确认：repo 注册路径不受限制；每个 server 设置统一 workspace 根目录并允许配置。
建议默认 `~/.cove/workspace`，使用 Cove 独立目录，不与 Orca 共用状态。
这里的 `~` 指执行 server 所属用户的 home，不是发起客户端的 home。

候选布局：

```text
<workspaceRoot>/<workspaceId>/
  server/         # 托管 worktree
  client/         # 托管 worktree
  docs/           # 既有 checkout 的入口，具体实现待验证
```

根目录规则约束 Cove 创建的工作位置，不自动移动用户选择的已有 checkout 或普通目录。
这些外部挂载保留真实绝对路径，通过 workspace 内入口访问；调查任务同样从 workspace root 启动。
Workspace 身份和挂载清单保存在 server 状态中，不从目录名反推所有权。
每个 workspace 都创建这一层入口目录；创建入口不要求创建 Git worktree，也不把入口初始化为 Git 仓库。

默认 cwd 已确定；外部目录入口可研究符号链接，但实际 agent 遍历、额外目录授权和 Git 行为仍需验证。
不能把符号链接当作透明授权，也不能因用户选择已有 checkout 而省略 workspace root。
不同仓库分别拥有 Git 状态，不创建伪 monorepo，也不自动移动注册 clone。

挂载切换不能仅靠原地重指 root 下的入口，否则旧会话即使 cwd 不变，后续访问也可能进入新仓库。
实现需保留活跃会话所绑定 revision 的目录映射；版本化入口是候选，不能安全保留时需用户结束旧会话后再切换。
具体目录布局仍待原型确定，不改变 workspace 身份和默认在 workspace root 启动的规则。

建议修改 workspaceRoot 只影响后续新建的 workspace；已有 workspace 保留记录中的原始路径，
后续往已有 workspace 加 repo 默认沿用它自己的根目录。迁移已有目录是独立操作，不由设置变更隐式触发。

## 5. 跨设备迁移

需要区分三种操作：

| 操作 | 发生了什么 | 是否保留原进程 |
| --- | --- | --- |
| 换客户端接入 | 手机或另一台电脑连接原执行主机 | 是，仍在原主机 |
| 迁移 workspace | 从目标主机已注册的仓库准备工作位置、分支和选定内容 | 否，进程不会随文件移动 |
| 复制 rollout（待定） | 复制选定的会话记录文件，作为历史或后续手动继续的材料 | 否，也不代表目标 agent 能识别该会话 |

**目标是同一 task 可以换执行设备；一期不迁移活进程，不承诺 agent session 无损迁移。**

文件存在、目标 agent 能发现会话、目标 agent 能正确继续会话是三个不同结果。
Cove 不为达到后两者而改写远端 agent 的索引库或 session 数据库；这类能力留到后续评估。

### 5.1 建议的迁移过程

1. **规划**：确认目标主机已有每个 repo 的注册，选择对应注册、工作位置、提交和需要携带的改动。
   缺少注册时先完成注册，再继续迁移；不代替用户隐式创建 clone。
2. **停止写入**：用户结束此 task 的相关活跃终端，核实来源写入已停止；无法核实时不继续交接。
3. **准备**：基于已注册的目标 clone 选择 checkout 或建立 task worktree，传输需要的本地提交和选定内容。
   来源有未推送提交时，不能假定目标 clone 已有这些提交；目标已有改动也不能直接覆盖。
4. **验证**：逐仓检查内容、Git 状态和基本运行环境；使用目标主机自己的认证。
5. **交接**：确认来源仍冻结写入，再切换整个 workspace 的活动位置；一期不支持同一 task 双端分叉写入。
6. **继续**：用户在目标 workspace root 打开新终端并启动 CLI；保留来源位置和旧 session 的历史。
   若支持并选择了 rollout 复制，单独报告复制结果，不把它作为 agent 已恢复的证明。

凭据、进程内状态、系统依赖、未列入迁移范围的文件不隐式复制。
普通目录也需要明确的内容传输方式，不能套用 Git 提交迁移的承诺。

### 5.2 失败和重试

- 每次迁移有持久的操作 ID、源 revision、目标清单和逐步结果。
- 准备失败时，当前活动位置仍为来源；目标的部分产物可识别、可重试。
- 一期建议整个 workspace 一起切换主机，避免部分仓库已在新主机、部分仍在旧主机的隐式状态。
- 元数据切换需要在明确的权威存储中做 revision 检查；权威节点及部署方式待定。
- 远端操作可能成功但响应丢失。重试前按操作 ID 查询结果，不能重复创建资源或启动 agent。
- 无法联系来源时记录 `unverifiable`，不把断线当成 `exited`，不自动执行双端交接。
- 不承诺跨主机文件、Git 和进程操作构成一个原子事务。
- 目标已经继续产生新改动后，“切回来源”是新一次迁移，不能直接恢复旧指针并宣称回滚完成。

来源资源不会因为成功切换就立即删除。是否清理、可清理什么，单独处理。

### 5.3 可选 rollout 复制的边界

这仍是候选能力，不是一期开工前提：

- 只复制用户选择的会话记录，保留来源文件，不默认同步整个 agent home。
- 记录来源 agent、原生会话 ID、目标文件和复制结果；同名文件不得静默覆盖。
- 来源仍在写入时，要明确处理快照边界，不能把截断记录宣称为完整会话。
- 默认不重写记录内的 cwd、历史路径、会话身份，也不更新 agent 自有数据库。
- 复制失败与 workspace 迁移失败分别报告；不把可选文件复制做成核心终端功能的依赖。
- 目标工具若不能直接使用这些文件，界面说明限制，由用户选择如何继续。

## 6. 生命周期与资源所有权

以下动作必须分开：

- 关闭视图：只关闭当前客户端页面。
- 归档 task：改变任务的可见性，不自动停止进程或删除目录。
- 停止 session：由执行主机确认具体进程实例的停止结果。
- 移除 mount：更新 workspace 的挂载关系，不等同于删目录。
- 删除托管 worktree：检查运行中的 session、未提交改动、未推送提交和共享引用后处理。

已有 checkout 和普通目录默认是外部资源；归档、删除 task、移除挂载都不能自动删除它们。
托管 worktree 记录创建来源和资源 ID；路径名符合某个前缀不是资源所有权证明。

Terminal session 应保存 tab ID、task ID、workspace revision、host ID、启动目录和当时的挂载映射。
默认启动在 workspace root，不能要求每个 session 必须绑定一个单独的 mount ID。
Agent 原生会话 ID 与终端进程实例 ID 分开。记录关联不授予 Cove 改写原生会话的职责。

客户端切换或重连不得重写这些事实。历史记录应能回答“这次修改在哪台设备、哪个仓库完成”。

## 7. Shepherd：后续独立集成

一期不依赖 Shepherd 的扫描器、数据库、模型判断、审批流程或看板服务。
Cove 自己完成任务创建、workspace 管理、session 操作和基本状态展示。

未来建议的分工：

- Cove 提供稳定的 task/workspace 身份，以及可查询的会话、挂载和迁移历史。
- Shepherd 负责跨工具整理工作、摘要、阶段建议和看板视图。
- 两者通过显式接口和外部 ID 映射集成，不直接互写数据库。
- Shepherd 可以把多个工作记录聚合成一个看板事项；它的聚合 ID 不替代 Cove 的执行任务 ID。
- 自动关联可以提出建议，不能仅凭相同 cwd、分支名或标题就合并 Cove task。
- Shepherd 判断任务完成，不等于授权停止 session 或删除 worktree。
- Cove 观察到进程退出，也不等于业务任务完成。

一期只需要保留这些身份边界，不预先实现事件总线、复杂同步系统或 Shepherd 专用协议。

## 8. 一期范围建议与待讨论项

### 建议纳入

- 一个 task 一个 workspace，单仓是默认简化视图。
- repo 提前注册，跨主机迁移要求目标 host 已有全部对应 repo 的注册。
- 创建菜单中可一次配置多个 repo/worktree，创建后仍可继续添加。
- 支持已有 checkout、独立 worktree、普通目录，以及一个 workspace 内多个仓库。
- 稳定的 task 身份与可变的挂载绑定，明确 session 不会随路径切换自动移动。
- 本地和远端 TUI 的创建、接入、重连；桌面与 mobile 操作同一个执行实例。
- 独立的 relay 协议版本、稳定实例发现、兼容性握手以及显式 recovery/reset。
- 独立持久 server、多客户端直连与同步、内置 Tailscale 和 host 网络接入。
- 主仓库转独立 worktree，先把清洁来源与已有改动场景的行为做清楚。
- 为跨主机迁移保留身份、revision 和操作记录设计。
- Relay 为数据传输提供独立调度与可恢复的操作身份，完整迁移范围另行确定。

### 一期明确不做

- 定时任务；调度与触发语义留到后续交付阶段。

- managed agent、接管 agent 执行循环。
- 独立 PTY keeper 与 server 重启后的活进程无损恢复。
- Chat UI 与 Web App（均为二期），以及 mobile 内嵌 Tailscale。
- agent 原生 session 无损迁移、活进程热迁移。
- 为会话迁移改写远端 agent 索引库或 session 数据库。
- Shepherd 运行时依赖或看板同步实现。

### 尚未承诺的一期能力

- 跨设备 workspace 文件迁移的具体范围，以及是否提供可选 rollout 复制。
- 支持哪些 agent 的识别与启动适配，以及各平台最低系统版本；chat 操作范围留待二期。
- Workspace root 已是统一默认入口；外部挂载实现、revision 映射和 agent 授权方式仍需验证。
- 同一共享 checkout 上多个可写 task 的限制策略。
- 各 host 的 server 持有本机执行和业务状态；跨 host 迁移交接和客户端离线可操作范围待细化。
- 桌面 Electron 与 host 的 Node 技术栈已定；mobile 的 RN + WebView 与首个终端后端 xterm.js 已定，Expo 工程方案和具体版本仍需确定。

这些是后续讨论项，不由本次文档默认决定。

## 9. 后续实现的验收场景

本文不包含实现；以下是实现前应转化为验证计划的关键场景。

- 调查任务使用已有 checkout，不创建多余 worktree；删除 task 不删来源目录。
- 注册含多个外部 worktree 的 repo 不增加 task 列表项；只显示 Cove 记录及显式挂载。
- 托管路径缺失时 task 仍在，显示异常；目录扫描不自动认领孤立目录。
- 创建菜单一次配置两个 repo/worktree，创建后得到一个 task 和完整的 workspace。
- 创建入口不能使用尚未注册的 repo；切换 host 后不错误复用另一主机的 repo 注册。
- 多仓迁移缺少任一目标 repo 注册时，提示补齐注册，不隐式 clone 或部分切换活动主机。
- 转入独立 worktree 后 task ID 不变；旧 session 仍正确显示原位置。
- 来源混有其他任务的改动时，不自动将全部内容认领或迁走。
- 两仓任务中一个仓库准备失败，不发布看似完整的新执行位置。
- 多仓任务中仅切换一个仓库的绑定，其他仓库和历史 session 保持真实对应。
- 手机切后台或桌面断线后，重新接入同一个远端 session，不重复启动 agent。
- macOS desktop 完全退出后，mobile 仍能直接读取 server 状态、创建任务并操作原有终端。
- 所有客户端断开后 server 持续运行，重新连接可获得共同的 task/workspace/终端清单。
- Tailscale 与 host 网络连接同一 server 身份，切换入口不复制任务或终端。
- 客户端更新但协议不变时，接回原 relay 和 PTY，不启动新 relay 或重新执行 agent。
- 协议不同时展示版本差异和恢复入口；仅打开新客户端不得停止、覆盖或绕过旧 relay。
- 连接失败、认证失败或当前实例找不到 session 时，不把旧 session 当成已退出并自动重建。
- 迁移目标包含未推送提交及选定工作内容；旧主机断线时不误判其进程已退出。
- 迁移请求响应丢失后重试，不重复创建 worktree、目录或执行实例。
- 跨设备后创建的是新终端，不显示为原 agent session 已无损迁移。
- 可选 rollout 复制不改写 agent 数据库，不覆盖同名文件，不声称复制成功等于恢复成功。
- Shepherd 未安装、离线或升级时，不影响 Cove 核心工作流。

## 10. Relay 的协议与升级边界

详见 [Relay 协议与生命周期](relay-protocol.md)。

- 发布版本只用于诊断和分发，不决定 relay 实例归属或通信是否兼容。
- 同协议版本的基础能力双向兼容；可选扩展显式协商。
- 客户端升级、退出、切换设备只改变连接，不应重启持有 PTY 的 relay。
- 跨协议版本保留现有工作，先明确展示不兼容及恢复方式。
- Recovery 优先重新接入原实例；reset 是可能终止会话的独立操作，必须说明影响并由用户明确执行。

上述是 core 的设计约束，不依赖 managed agent、rollout 迁移或 Shepherd。

Relay 的数据流与本地 tab 渲染候选方案见 [终端架构讨论](terminal-architecture.md)。
多客户端已确定由当前操作者控制输入和尺寸，通过终端 focus 协议自动切换。
首版终端已选择 xterm.js，mobile 使用 RN + WebView，保留可替换后端边界。
服务端已选 @xterm/headless；Server/CLI 已选择 TypeScript/Node.js，恢复格式与具体版本仍待设计和验证。

终端运行时已选 node-pty + @xterm/headless + @xterm/addon-serialize，通过 Cove 适配层补充恢复状态。
PTY 与唯一服务端权威模型同 worker；恢复优先补增量，有缺口时安装 VT 基线，历史有限。
恢复基线包含普通/备用屏幕必要状态，scrollback 可裁剪；客户端重排上下文不足时，尺寸变化后从 server 获取新基线再接续增量，不默认发送全部历史。
客户端按可见范围订阅实时输出：desktop 包括列表内可见终端预览，mobile 首期默认只订阅当前活跃终端；
其他终端通过列表接口取得最近快照。订阅与 focus 分离，后台终端的服务端模型仍持续更新。
具体版本、恢复兼容性、IPC 与流控仍需验证，见 [终端链路设计](terminal-architecture.md#33-首个运行时方案已选待原型验证)。
终端传输已确认采用 VT 字节流，不考虑字符网格快照/cell 增量；恢复基线通过 VT 序列与必要元数据表达。

## 11. 独立 Server、网络接入与多端同步

Relay 已明确为 host 上独立运行的持久 server，而非 desktop 的 SSH 转发子模块。
Server 负责本机 task/workspace、仓库注册、操作结果及终端事实；desktop/mobile/Web 都是直接客户端。
容量目标至少 100 个 agent TTY 经常同时输出，典型主机为 devbox；具体输出负载与端到端验收预算需量化。
已选择 Node 控制进程与有界终端子进程池隔离的结构，Go 组件负责内置 Tailscale。
runtime/worker 统一使用 pipe 帧协议承载控制和数据；进程数量及帧编码尚未冻结。
runtime 定期刷新全部终端的状态和最近快照，含不活动/无人订阅终端；严重落后的客户端订阅可由 server 主动终止，要求全量恢复后重新订阅。
业务持久化已选择每 host 本地 SQLite，驱动使用 better-sqlite3；终端原始输出不逐 chunk 写入业务数据库，执行线程尚未确定。
通信已选择 HTTP + WebSocket：HTTP 业务请求及文件传输，WebSocket 业务事件，独立终端 WebSocket 通道承载 VT 与终端控制。
网络框架已选择 Fastify + @fastify/websocket，HTTP 业务接口已选择 JSON-RPC 2.0，schema 工具已选择 Zod；领域服务与终端协议保持独立。
同步方案及持久边界见 [Server 架构](server-architecture.md)，其中具体机制仍标明为建议。

## 12. 定时任务：后续范围，不首发

建议由执行 host 的持久 server 调度，不依赖 desktop/mobile 在线。Schedule 与 Task 分开：
Schedule 保存触发规则、时区、执行 host、工作位置或创建模板；每次触发产生独立 Run 和结果记录。
这些是候选模型，尚未确定每次新建 task 还是使用已有 task。

后续实现时，建议从“按计划创建 task/workspace 并启动指定 CLI 命令”开始；
不默认往正在交互的终端注入 prompt，也不接管 agent 执行循环。
已有 task 上运行命令可以作为另一种显式目标，不能靠是否存在终端隐式选择。

实现调度前需冻结的语义：

- 一次性时间与重复规则、时区和夏令时的解释；是否允许错过时间后补跑。
- 主机离线不迁到其他 host 偷跑；建议恢复后默认跳过错过的周期，不集中补跑。
- 建议同一 schedule 的上次运行未结束时跳过本次并记录原因，不默认并发写同一工作目录。
- 每次计划触发有稳定 runKey；重复唤醒不重复创建资源。不承诺外部命令副作用恰好执行一次，
  启动结果不确定时保留待核实状态，不盲目重新执行。
- 进程退出码与 agent 是否完成业务目标分开；长期交互式 CLI 的完成判定不能仅靠终端安静。
- 暂停、取消后续触发、停止正在运行的 Run 分开；输出、退出原因、通知保留可查询记录。
- Schedule 默认绑定明确的执行 host；迁移 task 不自动迁移 schedule，避免来源和目标重复触发。

尚需用户确定主要用途：定期新建 agent 任务、对已有 task 追加工作，还是普通 shell 命令。
未实现调度时只保持领域边界，不预先实现空调度器或绑定未定的协议消息。

| --- | --- | --- |
| 平台最低版本与客户端工程 | Electron 与 mobile 的 RN + WebView 已定，Web App 经 Tailscale 已纳入二期；确定最低系统/浏览器版本与 Expo 工程方案；Lynx + WebGL / WebGPU 后续评估 | 决定安装、PTY、构建与发布成本 |
| 多仓 agent 入口 | 单仓/多仓均从 workspace root 启动；验证外部挂载、revision 映射与授权 | agent 要能实际访问多个 repo，不能只在 UI 显示挂载 |
| Host 间 task 权威交接 | 一个 workspace 同时只有一个活动 host；来源持久冻结写入后授权目标接收，失联不自动接管 | 稳定 task ID 不足以防止两个 server 都认为自己可写 |
| 配对实现 | 固定 serverId、一次性邀请与可撤销设备凭据已定；server CLI 开放配对端口，已配对 desktop 可申请新邀请供 mobile 使用；SSH/Tailscale 通道安全 + Cove 设备 token 已选；细化邀请兑换、凭据存储和撤销传播 | 首次连接、换入口和 server-to-server 传输都依赖它，详见 server 架构 §9.3–9.4 |
| 终端状态与技术栈 | 已选 xterm.js 与 node-pty/headless/serialize；以常用 TUI 验证快照、查询回复及尺寸事件 | 可靠重连不能依赖某个 UI 库的私有状态 |
| 首批 agent 的识别与启动 | 初版只支持 TUI；普通 CLI 均可运行，列出需要专门识别/启动的 agent | 识别状态不等于 managed agent；chat 适配留到二期 |

目录建议需要用实际 CLI 的目录权限、Git、路径解析和文件监听验证；不把符号链接当成透明挂载。
共享 checkout 建议显示共享警示、不自动独占加锁；Cove 锁也不能约束外部编辑器。
迁移允许传输的改动种类必须形成明确清单，包括本地提交、暂存状态、未跟踪文件和选择的目录；
不支持的项目在迁移前报告，不能悄悄丢弃。相关机制见 [Server 数据传输](server-architecture.md#61-relay-承载数据传输)。

建议第一个实现里程碑：独立 server + CLI + 单个真实 PTY + 两个客户端，验证无客户端继续运行、
交替 focus、不同尺寸观看、断线恢复、版本不兼容提示及大数据流并发时的终端响应。
技术验证可先使用两个最小客户端，最终必须在选定的真实移动端验证输入法、键盘和前后台恢复。
此里程碑不代表取消多仓、mobile、迁移或定时任务的产品需求。

## 14. CLI 是完整操作入口

已确认：Cove 提供原生 CLI，作为 first-class operator，按领域划分子命令。
CLI 是产品能力全集的操作接口，不只是 GUI 的辅助配置工具。后续每项新增业务能力和设置必须有完整 CLI 支持，
不能先实现 GUI-only 功能，再把 CLI 留为可选补齐项。初版仍不提供通用设置页面。
Agent 与脚本通过 CLI 使用同样的操作；不要求用户维护配置文件。

### 14.1 领域命令与统一操作接口

以下命令域是建议，名称与语法尚未实现或冻结：

| 命令域 | 能力范围 |
| --- | --- |
| `server` | 初始化、启动/维护、状态、网络入口与服务配置 |
| `auth` | 配对、设备清单、授权与撤销 |
| `repo` | 各 host 的仓库注册、检查与移除注册 |
| `task` / `workspace` | 任务生命周期、挂载、工作位置与迁移 |
| `tab` / `terminal` | 逻辑 tab、重开清单、PTY 启停/接入、输入输出、focus/resize 与活动状态配置 |
| `transfer` / `operation` | 数据传输，以及可查询、可等待、可继续的长操作 |
| `client` | 明确作用域的连接与显示偏好，不将当前设备配置误写到 server |
| 后续领域 | 定时任务、chat 等在其交付期同步提供完整命令与配置 |

示例：`cove --server devbox terminal config set idle-after 10m`。
命令需暴露可发现的选项与类型，不以通用 `set <任意 JSON 路径>` 作为全部配置能力的替代。
配置的 get/set/reset/schema/status 按领域提供；跨领域原子更新是否需要另行评估。

建议 CLI、desktop、mobile 使用同一领域操作接口、schema、权限与事件语义。
GUI 不通过拼接 shell 命令调用 CLI，也不绕过统一操作层直接修改数据库。
业务规则在执行 host 上仲裁，CLI 不是另一份业务权威；关闭 GUI 不影响 CLI 工作。
像素级动画与平台交互不要求机械翻译成命令，但其底层业务操作、状态和可配置项必须通过 CLI 可达。

### 14.2 新增能力的交付标准

- 完整覆盖相关的创建、读取、修改、删除/停止等适用操作，以及所有配置项；不用无意义的空 CRUD 凑齐形式。
- 提供 `--help`、参数约束、作用域、默认值和应用方式说明；既可交互使用，也可用显式参数非交互调用。
- 提供稳定的结构化输出模式、机器可识别错误与退出码；诊断/进度不污染结构化结果。
- 显式选择 server/资源身份，返回实际目标；路径由执行 host 解释，不能依赖当前打开的 GUI task。
- 长操作返回 operationId，支持状态查询与等待；按能力提供取消/重试，不将断开 CLI 等同于取消已接受操作。
- 配置及资源修改遵守 revision 与操作幂等规则；终端输入仍遵守其自身的去重和不确定性规则，不盲目重试。
- CLI 的终端接入同样参与 focus/controlEpoch 仲裁，不成为绕过其他操作者控制权的后门。
- 客户端私有显示偏好也有明确配置接口；远程目标不可达时报告不可达，不暗改另一设备或声称已生效。
- 配对/授权可从 CLI 发起、查询与完成 Cove 侧操作；外部身份提供者要求的浏览器/系统交互不因此取消。
- 随能力提供对应契约验证，包括 CLI 与 GUI 操作结果一致及混合版本行为；完整 CLI 覆盖是完成条件。

### 14.3 配置持久化与远程修改

CLI 提交语义化操作，由配置所属组件持久化；server 业务配置使用本地 SQLite，客户端本地偏好的存储另定。
内部存储实现不作为手工编辑契约。
可提供受校验的导入/导出用于备份，但运行不依赖配置文件，也不采用文件与数据库双写入源。
普通客户端布局与字体等偏好属于客户端；workspaceRoot、网络监听和服务端资源预算属于目标 server。
配置不等于 task/workspace 数据，设备密钥不混入普通设置导出。

Server 提供 schema、校验、revision、desired/effective 值和应用结果；CLI 与 GUI 使用同一套接口。
需要重启的变更报告 pending-restart，不因配置命令自动结束 PTY。
首次初始化/启动也提供 CLI 入口；服务尚未运行时使用明确的本机初始化流程，避免必须先运行服务才能设置启动参数。
具体一致性和远程修改语义见 [Server 配置](server-architecture.md#9-配置与设备授权)。
